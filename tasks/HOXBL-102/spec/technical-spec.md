## 4. 技術的に考慮すべき論点

### 4.1 システム境界

- **TS-001**
  - **論点**: 通知の発行責務をどの層に置くか（taskのユースケース内で直接発行するか、イベント発行と配信を分離するか）
  - **背景**: task追加（`CreateTaskUseCase`）・ステータス変更（`ChangeTaskStatusUseCase`）・優先度変更（`UpdateTaskUseCase`）は既存の`task`ドメインに属する一方、通知の送信先や設定は`viewer`/`project`ドメインの情報に依存する
  - **関連要件**: REQ-101, REQ-102, REQ-103
  - **検討メモ**: todo.mdでは`task_notification_events`テーブルへのINSERTと非同期ワーカーによる配信（Outboxパターン）が案として挙がっている。task／viewer双方のドメイン境界をまたぐため、責務分割の検討が必要
  - **確定状態**: 検討中

### 4.2 状態管理・整合性

- **TS-101**
  - **論点**: 通知イベントの発生（DB更新）と通知送信の整合性（DB更新は成功したが通知送信が失敗した場合の扱い、重複送信の防止）
  - **背景**: REQ-302は送信失敗時に再送信しない方針を定めているが、これは「送信を試みた上で失敗したら諦める」という業務要件であり、内部実装として送信試行自体を確実に1回行う仕組みまでは規定していない
  - **関連要件**: REQ-302, REQ-501
  - **検討メモ**: 現状`task`ユースケースに通知発行の仕組みがないことを確認済み（`app/server/src/task/application/`配下は永続化のみ）。DBトランザクションと通知発行のタイミング関係、重複防止の要否は後続設計で判断する
  - **確定状態**: 未確定

- **TS-102**
  - **論点**: `project_viewers`テーブルの通知ON/OFF属性の保存方式と、招待の新規有効化・復活時のON初期化タイミング
  - **背景**: 現状の`project_viewers`テーブル（`app/server/src/shared/database/schema.ts`）には通知設定に相当するカラムが存在しない。招待の`status`（active/revoked）とは独立した属性として扱う必要がある
  - **関連要件**: REQ-002, REQ-003, REQ-106
  - **検討メモ**: スキーマ変更（`project_viewers`への列追加、または別テーブル化）を伴う可能性がある。スキーマ駆動開発フローに従うこと
  - **確定状態**: 未確定

### 4.3 権限・公開範囲

- **TS-201**
  - **論点**: 通知ON/OFF設定の参照・変更を、当該viewer本人のアクセストークンに限定するアクセス制御の実装方式
  - **背景**: HOXBL-101で確立されたトークンベースのアクセス制御（RLSとは別レイヤ）を、通知設定の読み書きにも適用する必要がある
  - **関連要件**: NFR-101
  - **検討メモ**: 既存の`viewerAccessRoutes.ts`等のアクセス制御パターンを流用できるか確認が必要
  - **確定状態**: 検討中

### 4.4 入出力・バリデーション

- **TS-301**
  - **論点**: Web Push購読情報（エンドポイント・鍵）の登録・保存主体とタイミング
  - **背景**: 現状Web Push/VAPID/Service Workerの実装は存在しない（新規導入）。viewerはSupabase Authアカウントを持たないため、購読情報をどのキー（アクセストークン起点のviewer識別子等）に紐付けて保存するかの設計が必要
  - **関連要件**: REQ-001, REQ-301
  - **検討メモ**: ブラウザの通知許可状態（許可/未許可/拒否）とシステム内部の購読情報の有無をどう対応させるかも合わせて検討する
  - **確定状態**: 未確定

### 4.5 他システム・通知・受け渡し

- **TS-401**
  - **論点**: 通知イベント発生からWeb Push送信までの配信方式（同期/非同期）とリトライ方針
  - **背景**: todo.mdでは、DB更新と同一トランザクションで通知イベントテーブルにINSERTし、非同期ワーカーがpendingイベントを拾って配信するOutboxパターンが案として挙がっている。CLAUDE.mdの方針（リクエストパス上での無条件長時間リトライ禁止、リトライはallowlistベースの限定的なもの）との整合が必要
  - **関連要件**: REQ-101, REQ-102, REQ-103, REQ-302
  - **検討メモ**: REQ-302（送信失敗時は再送信しない）はビジネス要件としての最終決定だが、内部的な「一時的な接続エラー等での限定的リトライ」を送信試行の中に含めるかどうかは、CLAUDE.mdのリトライガイドライン（allowlist方式、fail-fast）に沿って後続設計で判断する
  - **確定状態**: 検討中

- **TS-402**
  - **論点**: ダイジェスト配信（将来拡張）を見据えた通知イベント記録の設計
  - **背景**: 今回はリアルタイム都度配信のみを実装するが、todo.mdでは将来的にダイジェスト配信を追加する可能性が残されており、その場合はイベントの書き込み側を変更せず集計バッチを追加するだけで対応できることが望ましいとされている
  - **関連要件**: なし（スコープ外だが設計上考慮）
  - **検討メモ**: 通知イベントの記録形式を、将来のダイジェスト集計処理からも参照できる形にしておくかどうかは、今回のスコープでは決定しない
  - **確定状態**: 前提あり（将来拡張点として設計上考慮するが、今回は実装しない）

### 4.6 監査・ログ・運用

- **TS-501**
  - **論点**: 通知送信の成功・失敗を運用上どこまで追跡可能にするか
  - **背景**: REQ-302により送信失敗時の自動リカバリは行わない方針が確定しているが、運用上の障害検知（大量失敗の把握等）の要否は要件として明示されていない
  - **関連要件**: REQ-302
  - **検討メモ**: 業務要件としての既読管理・履歴画面は対象外（スコープ外）だが、システム運用上のログ・メトリクス要否は別途検討が必要
  - **確定状態**: 未確定

## 5. 要件から見えたリスクと注意点

- **RISK-01**: Web Push・VAPID・Service Workerが未実装であるため、新規インフラ要素の導入が必要になる
  - **関連要件**: REQ-001
  - **影響**: 実装規模、インフラ構成
  - **備考**: なし

- **RISK-02**: `project_viewers`のスキーマ変更（通知ON/OFF属性の追加）は、スキーマ駆動開発フロー（generate:schemas → generate:openapi → generate:types）に従う必要がある
  - **関連要件**: REQ-002, REQ-003
  - **影響**: 既存のviewer関連スキーマ生成・型定義への影響
  - **備考**: `.claude/rules/schema-db.md`のガイドラインに従うこと

- **RISK-03**: taskのステータス変更・優先度変更ユースケースに通知発行の呼び出しを追加することで、既存のtaskドメインとviewer/project通知ドメインの結合が生じる
  - **関連要件**: REQ-102, REQ-103
  - **影響**: 既存task機能への影響範囲、テスト範囲
  - **備考**: なし

## 6. 後続の技術設計で確認すべき事項

- **TDQ-01**: 通知発行の責務分割（taskユースケースからの直接発行か、イベント発行と配信の分離か）
  - **理由**: task／viewer双方のドメイン境界にまたがるため、アーキテクチャ上の設計判断が必要
  - **関連要件**: REQ-101, REQ-102, REQ-103

- **TDQ-02**: `project_viewers`への通知ON/OFF属性の具体的なスキーマ設計
  - **理由**: 既存テーブルへの列追加か別テーブル化かで、招待復活時のON初期化ロジックの実装が変わる
  - **関連要件**: REQ-002, REQ-003, TS-102

- **TDQ-03**: Web Push購読情報の保存方式とviewer識別子（アクセストークン）との紐付け設計
  - **理由**: viewerがSupabase Authアカウントを持たない前提での新規設計が必要
  - **関連要件**: REQ-001, TS-301

- **TDQ-04**: 通知配信の同期/非同期方式とリトライ方針の確定
  - **理由**: CLAUDE.mdのリトライガイドライン（allowlist方式、fail-fast/fail-closed）との整合を取る必要がある
  - **関連要件**: REQ-302, TS-401

- **TDQ-05**: 既存`project_viewers`レコード（本要件リリース前からの有効な招待分）に対する通知ON初期化のマイグレーション方式
  - **理由**: REQ-004により、新規招待分だけでなく既存招待分も一律ONとすることが確定した。リリース時に既存レコードへ一括で初期値を適用する移行処理（マイグレーションスクリプト等）の設計が必要
  - **関連要件**: REQ-004, TI-REF-05

- **TDQ-06**: 通知の想定発生頻度・ボリュームの見積もり
  - **理由**: NFR-001によりレート制限等の抑制は導入しない方針が確定したが、実際にどの程度の頻度で通知が発生しうるかは実測データがなく未確認。想定project数・viewer数・task変更頻度をもとにした見積もりが、Web Push配信基盤（TS-301, TS-401）のキャパシティ設計の前提として必要になる
  - **関連要件**: NFR-001, TI-REF-06
