## Phase 2: ヒアリング（質問と回答）

**Q1. todo.mdに「（検討中）部下（タスク作成者/変更者）への通知」との記載がありますが、今回のHOXBL-102のスコープに部下への通知（viewerのリアクション発生時など）を含めますか？**
A1. 含めない（viewerへの通知のみ）

**Q2. viewerはproject単位で通知ON/OFFを設定できますが、projectにviewerとして招待された直後の初期状態はどちらですか？**
A2. ON（招待/復活時点で自動的に通知を受け取れる状態にし、必要ならviewer自身がOFFにする）

**Q3. Web Pushとメールは「併用/フォールバック」と記載がありますが、業務的にはどのような使い分けを期待しますか？**
A3. 今回のリアルタイム変更通知はPushのみ（将来的な想定ではダイジェストのみメール）

**Q4. viewerがブラウザでWeb Push通知を許可していない（未許可・拒否）場合、その回の通知はどう扱うべきですか？**
A4. 何も送らない（保留・再試行はしない）

**Q5. 通知（Web Push）をタップ・クリックしたとき、viewerは何を確認できれば十分ですか？**
A5. 該当taskが含まれるviewer閲覧画面に遷移

**Q6. 優先度変更の通知について、業務上の意味を正確にするため確認します。通知の内容には何が十分ですか？**
A6. task名と「優先度が変えられた」という事実のみ（変更前後の具体値は含めない）

**Q7. 同一taskに対して短時間に複数の変更（例: ステータス変更と優先度変更が続けて）が発生した場合、通知はどうあるべきですか？**
A7. イベントごとに個別に通知（1通にまとめない）

**Q8. viewerが自分の通知ON/OFF設定を変更するための入り口はどこを想定しますか？**
A8. viewerのトークン付き閲覧画面自体から設定（別途専用ページは不要）

**Q9. Web Pushの送信自体が失敗（例: ブラウザ購読の期限切れ・無効化）した場合、業務上の期待動作は何ですか？**
A9. あきらめて終了する（リトライしない）

**Q10.「タスクが追加された」イベントは、どの操作を指しますか？**
A10. projectに新規taskが作成された時のみ（既存taskの所属project変更は「追加」に含めない）

**Q11.「ステータスが変わった」通知の対象は、すべてのステータス遷移ですか、それとも特定の遷移のみですか？**
A11. すべてのステータス遷移（逆戻りも含む）

**Q12. viewerが途中で見逃した通知をあとから一覧で確認できる履歴画面は必要ですか？**
A12. 不要（Push通知の即時性で十分とし、履歴一覧・既読管理は今回のスコープ外）

**Q13. viewerは複数projectに横断して招待されうるため、通知内容には「task名」に加えて「project名」も含める必要がありますか？**
A13. 含める（どのprojectの変更かを区別できるようにする）

## Phase 2追加: 未決事項に関する追加ヒアリング

**Q14. OQ-01: 本要件のリリース前から既に有効な招待を受けているviewerに対する、通知ON/OFF設定の初期値の遡及適用方針は？**
A14. 初期値ONでOK（新規招待分と同様、既存招待分も一律ON）→ REQ-004として確定

**Q15. OQ-02: 大量のイベントが短時間に連続発生した場合の、業務上の通知過多に対する懸念の有無は？**
A15. 基本的に許容する（レート制限等の抑制は導入しない）→ NFR-001として確定。ただし「多い場合はどの程度の頻度で発生しうるか知りたい」との補足があったが、現時点で実測データがなくこの場では回答不能。業務要件としての抑制方針は確定済みのため、頻度の見積もり自体は技術設計側の検討事項（TDQ-06 / TI-REF-06）としてtechnical-spec.mdに引き継いだ
