## 4. 技術的に考慮すべき論点

### 4.1 システム境界

- **TS-001**
  - **論点**: viewerのアクセス制御を、既存のuser単位RLSと同一レイヤに実装するか、API層（Hono）に独立した検証レイヤを設けるか
  - **背景**: viewerはSupabase Authユーザーではないため、`auth.uid()`ベースのRLSだけでは完結しない
  - **関連要件**: NFR-102, REQ-104, REQ-301
  - **検討メモ**: 既存のPostgreSQLProjectRepository/RLS設定（setup-rls.ts）とどう共存させるか、viewer専用のデータアクセス経路を分離するかは要検討
  - **確定状態**: 未確定

### 4.2 状態管理・整合性

- **TS-101**
  - **論点**: アクセストークンとメールアドレス・招待（project×email）の関係をどうモデル化するか（トークンはメールアドレス単位で1件、招待はproject×emailで複数、という多重構造の整合性）
  - **背景**: REQ-102/103/501/502で「既存トークン維持」「新規発行」「同一project再招待時の期限切れ判定」という複数の分岐が定義されている
  - **関連要件**: REQ-102, REQ-103, REQ-501, REQ-502
  - **検討メモ**: 招待テーブルとトークンテーブルを分離するか一体化するか、トークンの有効期限判定と招待の有効・無効判定をどう連動させるかは設計判断が必要
  - **確定状態**: 検討中

- **TS-102**
  - **論点**: 招待の取り消し（revoke）のデータ表現（論理削除／ステータスフラグ）をどう実装するか
  - **背景**: REQ-503により「取り消し済みのproject×メールアドレスへの再招待は、新規招待ではなく取り消し前の関係を復活させる」ことが業務要件として確定した。また、取り消し済みの招待はREQ-105の招待一覧から完全に非表示にする必要がある。この2つを両立するには、取り消し済みレコードを削除せず保持したまま一覧クエリで除外する設計が必要になる
  - **関連要件**: REQ-105, REQ-106, REQ-503
  - **検討メモ**: 論理削除（ステータスフラグ）による表現が有力だが、具体的なカラム設計・状態遷移（有効→取り消し→復活）は後続の技術設計で確定する
  - **確定状態**: 検討中

### 4.3 権限・公開範囲

- **TS-201**
  - **論点**: fail-closedの具体的な実装（無効トークン・期限切れトークン・招待0件状態をどう区別して判定するか）
  - **背景**: REQ-301（無効トークン拒否）とREQ-201（有効トークンだが招待0件は許可）を区別する必要がある
  - **関連要件**: REQ-201, REQ-301, REQ-306
  - **検討メモ**: トークンの検証（存在・失効・期限切れ）と、招待の有無の判定を別ステップとして設計する必要がある
  - **確定状態**: 検討中

### 4.4 入出力・バリデーション

- **TS-302**
  - **論点**: アクセストークンの生成方式（エントロピー、文字種、長さ）と保存方式（平文保存かハッシュ化か）
  - **背景**: NFR-101（推測困難なランダム値）を満たすための具体的な実装が必要
  - **関連要件**: NFR-101
  - **検討メモ**: トークンをDBに平文保存するか、ハッシュ化して保存し照合時に再ハッシュするかはセキュリティ設計として要判断
  - **確定状態**: 未確定

### 4.5 他システム・通知・受け渡し

- **TS-401**
  - **論点**: 招待メール送信の同期／非同期方式と、失敗時のロールバック実装
  - **背景**: REQ-303は「メール送信失敗時は招待自体を成立させない」ことを要求している。CLAUDE.mdはリクエストパス上での無条件長時間リトライを禁止しており、招待操作というリクエストパス上でメール送信を同期的に行い失敗を即座に判定する設計と、既存の③通知機能で想定されているOutboxパターン（非同期ワーカー経由）との整合を検討する必要がある
  - **関連要件**: REQ-303
  - **検討メモ**: 招待メールは「即時に成立可否をproject作成者へ返す」という要件上、③のOutboxパターンとは異なる同期的な送信が必要になる可能性があるが、その場合のリトライ方針（allowlist、タイムアウト）は別途設計が必要
  - **確定状態**: 検討中

- **TS-402**
  - **論点**: アクセストークンをタスク更新等のアクティビティに応じて自動延長する案（TI-REF-05）の採否
  - **背景**: ヒアリングの中でproject作成者から「利便性のため有効期限を自動延長できないか」という案が出たが、セキュリティ上のベストプラクティスとの兼ね合いで確定しなかった
  - **関連要件**: REQ-004
  - **検討メモ**: 固定期限とアクティビティ連動延長のどちらを採用するかは、セキュリティ（不正利用リスク）と利便性（リンク切れによる再招待の手間）のトレードオフとして後続の技術設計で判断する
  - **確定状態**: 未確定

### 4.6 監査・ログ・運用

- **TS-501**
  - **論点**: 招待・取り消し・トークン再発行の操作ログをシステム運用上どこまで記録するか
  - **背景**: REQ-105により招待済みviewer一覧は「現在有効な招待のみ」を表示し、取り消し済みは完全非表示にすることが確定した。ただし、この「業務上ユーザーに見せる一覧」とは別に、障害調査や不正利用調査のための運用ログ（誰がいつ招待・取り消し・再発行を行ったか）を残すかどうかは業務要件として問われておらず未確認
  - **関連要件**: NFR-201, REQ-105
  - **検討メモ**: ユーザー向け表示（完全非表示）と、運用者向けログの保持要否は別問題として切り分けて検討する
  - **確定状態**: 未確定

## 5. 要件から見えたリスクと注意点

- **RISK-01**: アクセストークンをメールアドレス単位で集約する設計（REQ-103）は、招待対象のメールアドレスの実在性・所有者確認を行わないため、第三者が誤ったメールアドレスを招待した場合に意図しない相手へ情報が渡るリスクがある
  - **関連要件**: REQ-101, REQ-103
  - **影響**: セキュリティ・情報漏洩
  - **備考**: メールアドレス確認（本人到達性の担保）は招待メール送信自体が兼ねる設計だが、それ以上の追加検証は今回のスコープで確認されていない

- **RISK-02**: 招待取り消し（REQ-106）がAPI層のトークン検証キャッシュ等に即時反映されない場合、取り消し後も一定時間閲覧できてしまう可能性がある
  - **関連要件**: REQ-106
  - **影響**: 権限制御の即時性
  - **備考**: キャッシュ方針が導入される場合は別途整合性設計が必要

- **RISK-03**: 招待メール送信をリクエストパス上で同期的に行う設計にした場合、SES等の外部サービス遅延がAPIレスポンス時間に直結し、CLAUDE.mdの「リクエストパス上での無条件長時間リトライ禁止」方針と抵触しうる
  - **関連要件**: REQ-303
  - **影響**: パフォーマンス・可用性
  - **備考**: 同期判定が必要な要件（REQ-303）と非同期配信を前提とする③の設計方針との整合を技術設計で確認する

## 6. 後続の技術設計で確認すべき事項

- **TDQ-01**: アクセストークンの生成・保存・検証方式（ハッシュ化の要否含む）
  - **理由**: NFR-101を満たす具体的な実装が必要
  - **関連要件**: NFR-101

- **TDQ-02**: 招待（project×email）とアクセストークン（email単位）のデータモデル設計
  - **理由**: REQ-102/103/501/502の分岐ロジックを正しく実装するための土台になる
  - **関連要件**: REQ-102, REQ-103, REQ-501, REQ-502

- **TDQ-03**: 招待メール送信の実装方式（同期/非同期）と失敗時のロールバック
  - **理由**: REQ-303とCLAUDE.mdのリトライ方針の両立が必要
  - **関連要件**: REQ-303

- **TDQ-04**: 取り消し済み招待を「一覧には出さないが再招待で復活できる」状態として保持するためのデータ表現（論理削除かステータス遷移か）
  - **理由**: REQ-105（完全非表示）とREQ-503（復活）を両立する実装方式の決定が必要
  - **関連要件**: REQ-105, REQ-106, REQ-503

- **TDQ-05**: アクセストークンのアクティビティ連動延長案（TI-REF-05）の採否
  - **理由**: 固定期限かどうかでトークン管理の実装が大きく変わる
  - **関連要件**: REQ-004
