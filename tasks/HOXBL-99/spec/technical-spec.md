## 4. 技術的に考慮すべき論点

### 4.1 システム境界

- **TS-001**
  - **論点**: project を新規ドメイン（project/domain, application, infrastructure, presentation）として独立させるか、既存task domainの一部として扱うか
  - **背景**: 本プロジェクトはドメインファースト構成（DDD + クリーンアーキテクチャ）を採用しており、project は task から参照される独立したライフサイクルを持つエンティティである
  - **関連要件**: REQ-001, REQ-101, REQ-107
  - **検討メモ**: project は今後②viewer招待、③通知、④リアクションの起点にもなるため、独立ドメインとして切り出す方が拡張性が高いと考えられるが、断定はしない
  - **確定状態**: 検討中

### 4.2 状態管理・整合性

- **TS-101**
  - **論点**: task.project_id を DB上NOT NULLにできるか、NULL許容のままにするか
  - **背景**: 既存taskはproject未所属のまま保持する（REQ-003）一方、新規taskは作成時にprojectが必須（REQ-102, REQ-302）
  - **関連要件**: REQ-003, REQ-102, REQ-302, REQ-201
  - **検討メモ**: DBスキーマとしてはNULL許容カラムとし、アプリケーション層（バリデーション）で新規作成時のみ必須とする案が考えられるが、CHECK制約や作成経路の分岐方法は後続設計で判断する
  - **確定状態**: 未確定

- **TS-102**
  - **論点**: 既存taskへの `project_id` カラム追加のマイグレーション手順（Drizzle migrate、CI/CDでのpreview/production適用順序）
  - **背景**: `.claude/rules/schema-db.md` に定義されたマイグレーション運用フロー（generate → migrate）に従う必要がある
  - **関連要件**: REQ-003
  - **検討メモ**: 既存データへの影響がない追加のみ（NULL許容カラム追加）であることを前提にマイグレーション設計を行う
  - **確定状態**: 前提あり

### 4.3 権限・公開範囲

- **TS-201**
  - **論点**: project一覧・project詳細・project選択肢の取得、およびprojectの編集・taskのproject_id更新における「作成者本人のみ」アクセス制御の実現方式
  - **背景**: usersテーブルとtasksテーブルは既存でRLS（Row Level Security）による user 単位アクセス制御が想定されている（schema.ts内コメント参照）。project にも同様の考え方が必要
  - **関連要件**: REQ-104, REQ-105, REQ-106, REQ-107, REQ-303, REQ-305, NFR-101
  - **検討メモ**: 既存task同様、project にも owner（作成者）カラムを持たせ、RLSないしAPI層でuser_idベースのフィルタを行う方式が候補となるが、どちらの層で担保するかは既存実装パターンとの整合を踏まえて後続設計で判断する
  - **確定状態**: 検討中

### 4.4 入出力・バリデーション

- **TS-301**
  - **論点**: project名（100文字以内・trim後非空）、説明文（上限なし）というrequirements.mdで確定した制約値を、DB制約・Zodスキーマのどちらで担保するか
  - **背景**: 既存taskのtitleには `length(trim(title)) > 0` および `length(title) <= 100` のCHECK制約があり、同様のパターンが流用できる可能性がある
  - **関連要件**: REQ-001, REQ-301, REQ-304, REQ-306
  - **検討メモ**: 制約の「値」自体はrequirements.mdで確定済み。DBのCHECK制約とアプリケーション層（Zodスキーマ）のどちらで一次的に検証するか、二重に持つかは既存taskの実装パターンとの整合を踏まえて後続設計で判断する
  - **確定状態**: 前提あり

- **TS-302**
  - **論点**: task作成・編集APIおよびproject作成・編集APIのリクエスト/レスポンススキーマ設計（Zodスキーマ、shared-schemas、OpenAPI生成への反映）
  - **背景**: 本プロジェクトはZodスキーマをバックエンド・フロントエンドでシェアし、スキーマ駆動開発を行っている
  - **関連要件**: REQ-101, REQ-102, REQ-103, REQ-107, REQ-302
  - **検討メモ**: `generate:schemas` → `generate:openapi` → `generate:types` のスキーマ駆動フローに従う前提（.claude/rules/schema-db.md）。具体的なスキーマ構造は後続設計で確定する
  - **確定状態**: 前提あり

- **TS-303**
  - **論点**: project詳細画面での「そのprojectに紐づくtaskのみを表示する」（REQ-106）を、どのレイヤ（DBクエリ条件／アプリケーション層でのフィルタ）で実現するか。また将来的な汎用task絞り込み機能（ステータス・優先度等との組み合わせ、スコープ外）と検索の実装基盤を共有できるか
  - **背景**: ヒアリングにおいて、project詳細でのtask表示は「結局絞り込みと同じロジックを使いそう」という見立てがユーザーから示されている
  - **関連要件**: REQ-106, TI-REF-03（requirements.md）
  - **検討メモ**: project_idを検索条件とする最小限のクエリで今回は実現可能と見込まれるが、将来の汎用絞り込み機能を見据えた検索条件の抽象化を今回の設計でどこまで行うかは判断が必要
  - **確定状態**: 検討中

## 5. 要件から見えたリスクと注意点

- **RISK-01**: project_id をNULL許容のまま運用し続けると、将来「project未所属taskの扱い」（②viewer招待・閲覧での表示可否など）が仕様として肥大化する可能性がある
  - **関連要件**: REQ-003, REQ-201
  - **影響**: データ整合性、②viewer招待・閲覧機能の設計難度
  - **備考**: ②以降の設計時に、project未所属taskをviewer閲覧対象からどう除外するか改めて検討が必要

- **RISK-02**: project名の重複を許可するため、UI・API上でprojectを一意に識別する手段は名前ではなくIDに限定する必要がある
  - **関連要件**: REQ-002
  - **影響**: フロントエンドでのproject選択UI、API設計
  - **備考**: 特になし

- **RISK-03**: project詳細でのtask絞り込み表示（REQ-106）の実装を、将来の汎用絞り込み機能を見据えすぎて過度に抽象化すると、今回のスコープ（project単位の表示のみ）を超えた設計になりうる
  - **関連要件**: REQ-106
  - **影響**: 実装コスト、設計の複雑化
  - **備考**: 今回はproject_idによる最小限のフィルタとして設計し、汎用化は将来必要になった時点で検討する方針が望ましいと考えられるが、断定はしない

## 6. 後続の技術設計で確認すべき事項

- **TDQ-01**: project ドメインの新設方針（独立ドメインとするか、既存task配下に含めるか）
  - **理由**: DDD構成上の責務分割方針を確定する必要がある
  - **関連要件**: REQ-001, TS-001

- **TDQ-02**: task.project_id のDBレベル制約（NULL許容/NOT NULL、CHECK制約の要否）
  - **理由**: 既存task・新規taskで必須性が異なるため、DB制約とアプリ層バリデーションの役割分担を決める必要がある
  - **関連要件**: REQ-003, REQ-102, TS-101

- **TDQ-03**: project・taskのアクセス制御をRLSで実現するかAPI層で実現するか
  - **理由**: 既存実装パターン（usersテーブルの外部キー制約に基づくcascade、tasksのuser_id単位インデックス）との整合を確認する必要がある
  - **関連要件**: REQ-104, REQ-303, REQ-305, NFR-101, TS-201

- **TDQ-04**: project名・説明文の制約（100文字以内・trim後非空、説明文は上限なし）を、DB CHECK制約とZodスキーマのどちらで一次検証とするか
  - **理由**: 既存task.titleの実装パターン（DB CHECK制約 + Zodスキーマの二重チェック）を踏襲するかどうかは設計判断が必要
  - **関連要件**: REQ-001, REQ-301, REQ-304, REQ-306, TS-301

- **TDQ-05**: project詳細でのtask絞り込み表示の実装を、将来の汎用絞り込み機能を見据えてどこまで抽象化するか
  - **理由**: 過度な抽象化はスコープ超過、過度な個別実装は将来の手戻りにつながるため、設計判断が必要
  - **関連要件**: REQ-106, TS-303, RISK-03
