# project基盤 要件定義書

## 1. 概要

- **Requirement ID**: HOXBL-99
- **目的**: `task` を束ねる `project` エンティティを新設し、上長への進捗共有機能（viewer招待・通知・リアクション）を積み上げるための土台を作る
- **背景**: 上長がプロジェクトを横断して進捗・優先度を把握できるようにする一連の機能（②viewer招待・閲覧、③通知、④リアクション）は、いずれも「project単位でtaskをまとめられること」を前提とする。①project基盤はその前提を満たす最初のステップ
- **対象**: `project` エンティティの新設、`task` と `project` の紐付け（作成時必須選択・後からの変更）、自分が作成した `project` の一覧表示、projectの名称・説明文の編集、project詳細画面でのそのprojectに属するtaskのみの表示
- **対象外**: project の削除、他ユーザーが作成した project の閲覧、viewer招待、通知、リアクション、organization/backlog/backlogItem階層

## 2. 用語定義

- **project**: taskを束ねるための新設エンティティ。名前（必須）と説明文（任意）を持つ
- **project未所属task**: project_id が設定されていないtask。今回の移行で発生する既存taskの状態
- **作成者**: projectまたはtaskを作成したログイン済みユーザー本人

## 3. ユーザーと利用条件

### 3.1 主な利用者

- **ログイン済みユーザー（既存のtask利用者。上長への進捗共有機能の文脈では「部下」に相当）**: 自分のtaskをprojectという単位でまとめて管理する

### 3.2 関係する利用者

- 今回のスコープでは、project/taskの作成者以外の利用者（上長など）は登場しない（②以降で対応）

### 3.3 利用条件

- ログイン済みユーザーであれば誰でもprojectを作成できる
- 自分が作成したprojectおよびtaskのみ閲覧・操作（編集を含む）できる
- 他ユーザーが作成したprojectの情報は閲覧・編集できない

## 4. 前提条件・依存関係

### 4.1 前提条件

- 既存のtask機能（作成・一覧・更新・削除）が稼働していること
- ユーザーはSupabase Authによるログイン済みであること

### 4.2 依存関係

- ②viewer招待・閲覧、③通知、④リアクションは、いずれも本要件（project基盤）の完了を前提とする

### 4.3 既知の制約

- なし（今回のスコープにおいて業務上の制約は確認されていない）

## 6. データ要件

### 6.1 入力情報

- **project名**
  - **必須/任意**: 必須
  - **形式**: 文字列
  - **制約**: 前後の空白を除いた結果が1文字以上100文字以内であること。同一ユーザー内での重複は許可する
  - **備考**: 既存taskのtitleと同一ルール

- **project説明文**
  - **必須/任意**: 任意
  - **形式**: 文字列
  - **制約**: 文字数上限は設けない
  - **備考**: 既存taskのdescriptionと同一ルール

- **taskの所属project**
  - **必須/任意**: task新規作成時は必須。既存taskは未所属状態を許容し、後から任意のタイミングで設定・変更できる
  - **形式**: 自分が作成したprojectの中から1件選択
  - **制約**: 他ユーザーが作成したprojectは選択不可
  - **備考**: なし

### 6.2 結果として必要な情報

- **project一覧**
  - **用途**: 表示（自分が作成したprojectの一覧確認、task作成・編集時の選択肢表示）
  - **備考**: なし

- **project詳細に紐づくtask一覧**
  - **用途**: 表示（project詳細画面で、そのprojectに属するtaskのみを確認する）
  - **備考**: なし

### 6.3 バリデーション

- project名は、前後の空白を除いた結果が空文字列であってはならない（空白のみの入力は未入力として扱う）
- project名は100文字以内でなければならない
- taskの所属projectには、操作者本人が作成したproject以外を指定できない
- 上記のバリデーションはproject作成時・編集時のいずれにも適用する

### 6.4 保存・更新に関する業務ルール

- projectは作成者本人に紐付けて保存する
- projectの名称・説明文は作成者本人が編集できる
- 既存taskのproject所属先は、ユーザーが編集操作を行うまで未所属のまま変更しない
- project自体の削除は今回のスコープに含まない（14. スコープ外を参照）

## 7. 他部門・他システムとの受け渡し

- 今回のスコープにおいて、他部門・他システムとの受け渡しはない

## 9. ユーザーストーリー

- **US-01**
  - **私は**: ログイン済みユーザー
  - **複数のtaskを扱う中で、目的ごとにtaskをまとめたい場面において**: 個々のtaskがどの取り組みに属するか整理できていない状況で
  - **projectを作成し、taskをprojectにまとめたい**: projectという単位でtaskを分類したい
  - **そうすることで**: 自分のtaskをproject単位で把握できるようになり、将来の上長への進捗共有（②以降）の土台ができる
  - **関連要件**: REQ-001, REQ-002, REQ-101

- **US-02**
  - **私は**: ログイン済みユーザー
  - **新しいtaskを作成する場面において**: どのprojectの取り組みかを明確にしたい状況で
  - **taskの作成時に所属projectを選びたい**: taskとprojectを最初から紐付けたい
  - **そうすることで**: taskがどのprojectに属するか一目でわかる
  - **関連要件**: REQ-102, REQ-105, REQ-302

- **US-03**
  - **私は**: ログイン済みユーザー
  - **project導入前から存在する既存のtaskを扱う場面において**: まだどのprojectにも属していないtaskがある状況で
  - **既存taskを後からprojectに割り振りたい**: 移行のタイミングを自分で選びたい
  - **そうすることで**: 一括移行によるデータ変更を気にせず、必要な範囲から整理できる
  - **関連要件**: REQ-003, REQ-103, REQ-201

- **US-04**
  - **私は**: ログイン済みユーザー
  - **projectを作成した後に、名前や説明文を見直したい場面において**: 当初つけた名前や説明が実態と合わなくなった状況で
  - **projectの名称・説明文を編集したい**: projectの情報を最新の状態に保ちたい
  - **そうすることで**: projectの内容が実態と乖離しない
  - **関連要件**: REQ-107, REQ-304, REQ-305, REQ-306

- **US-05**
  - **私は**: ログイン済みユーザー
  - **複数のprojectにtaskが分かれている場面において**: 特定のprojectの状況だけを確認したい状況で
  - **あるprojectを開いたときに、そのprojectのtaskだけを見たい**: 他のprojectのtaskに惑わされず対象を確認したい
  - **そうすることで**: project単位でtaskの状況を素早く把握できる
  - **関連要件**: REQ-106

## 11. 差分整理

### 11.1 既存仕様との差分

- task作成フローに「project選択（必須）」の入力ステップが新たに加わる
- taskはproject_idという新しい外部キーを持つようになる（既存taskはNULL、以後の新規taskはNOT NULL相当）
- project一覧・project詳細（そのprojectに属するtask一覧）・project編集という新しい画面/操作が追加される

### 11.2 既存運用との差分

- これまでtaskはuserにのみ紐付いていたが、今回からproject単位での分類が可能になる
- 既存taskは自動移行されず、ユーザーが必要に応じて手動でprojectへ割り振る運用に変わる
