# メールパスワード認証追加 技術設計メモ

- **Requirement ID**: HOXBL-94
- **参照要件書**: tasks/HOXBL-94/spec/requirements.md

## 4. 技術的に考慮すべき論点

### 4.1 システム境界

- **TS-001**
  - **論点**: 既存の Google OAuth 用クライアント実装（`app/client/src/features/auth/services`, `hooks/useOAuthCallback.ts` 等）にメールパスワードフローを追加する際の、サービス層・hooks 層の責務分割。
  - **背景**: 既存は OAuth コールバック前提のサービス群。メールパスワードフローはコールバックを伴わないため、抽象化の見直しが必要になり得る。
  - **関連要件**: REQ-001, REQ-103
  - **検討メモ**: 既存 `authService` への追加か、新規サービスとして分離するか、`providers/` のディレクトリ意図（OAuth プロバイダ抽象）と整合するかを設計時に判断。
  - **確定状態**: 未確定

- **TS-002**
  - **論点**: サーバー側認証ミドルウェア（`app/server/src/user/presentation/middleware/auth`）はトークン検証ベースのため、認証方式が増えても境界には影響しないと見込まれるが、ユーザー解決ロジック（同一性判定）への波及を確認すべき。
  - **背景**: REQ-002 により「同一メール＝同一ユーザー」を保証する必要があるため、user ドメインのアグリゲート／リポジトリでの同一性判定方式を確認する必要。
  - **関連要件**: REQ-002
  - **検討メモ**: ユーザー作成のトリガー（初回サインイン時の upsert 等）が認証方式によって分岐するかを確認。
  - **確定状態**: 未確定

### 4.2 状態管理・整合性

- **TS-101**
  - **論点**: 同一メールアドレスに対して Google identity と email identity を 1 ユーザーに紐づける identity linking の方式とタイミング。
  - **背景**: REQ-002 / REQ-302 を満たすには、サインアップ時に既存ユーザーの存在を検知し、新規ユーザーを作らずに案内を返す必要がある。Supabase Auth 側の identity linking 機能（手動／自動）と、サーバー側ユーザー集約での解決を整理する必要。
  - **関連要件**: REQ-002, REQ-302
  - **検討メモ**: Supabase の自動 linking 設定／手動 linking API のどちらを採るか、Google ユーザーへ「パスワード追加」を許可するフローと整合するかを設計時に決定。
  - **確定状態**: 未確定

- **TS-102**
  - **論点**: 確認メール未受領状態のアカウントに対する状態モデル（pending → confirmed）。
  - **背景**: REQ-201 / REQ-303 を実装する際、フロント側はサインインレスポンスから「未確認」を識別して UI 表示を分岐する必要がある。
  - **関連要件**: REQ-201, REQ-303
  - **検討メモ**: Supabase Auth から返るエラー種別と、フロントの表示分岐／再送導線実装の有無（OQ-02）を設計時に確定。
  - **確定状態**: 未確定

### 4.3 権限・公開範囲

- **TS-201**
  - **論点**: テストユーザー作成のための管理者経路。
  - **背景**: REQ-106 を満たすには、確認メール送信をバイパスしてアカウントを「確認済み」として作成する経路が必要。Supabase Admin API（service_role 鍵）の使用範囲・実行環境・実行権限を整理する必要。
  - **関連要件**: REQ-106
  - **検討メモ**: シードスクリプト（ローカル／Preview 環境）／管理 CLI／専用エンドポイントのいずれを採るか、本番環境での経路は閉じるかを設計時に判断。service_role 鍵の取り扱いと監査上の責務分離も検討対象。
  - **確定状態**: 未確定

### 4.4 入出力・バリデーション

- **TS-301**
  - **論点**: パスワードポリシー（大文字・小文字・記号含む 8 文字以上）の実装層と Supabase Auth ダッシュボード設定の整合。
  - **背景**: 業務ポリシーは確定（Supabase Auth ダッシュボードで設定）。フロント側のバリデーション表示と Supabase 側の制約が乖離しないよう設計時に確認が必要。
  - **関連要件**: REQ-101, REQ-105
  - **検討メモ**: クライアント側バリデーションのみではバイパス可能なため、Supabase Auth ポリシーを正として扱い、フロント側はユーザー体験向上のための補助バリデーションとして位置づける。
  - **確定状態**: 前提あり（ポリシーは確定。実装層の責務分担は設計時に判断）

- **TS-302**
  - **論点**: メールアドレスの同一性判定における正規化（大文字小文字、前後空白）。
  - **背景**: REQ-002 / AC-05 で「同一メール＝同一ユーザー」とする以上、正規化方針が必要。
  - **関連要件**: REQ-002, AC-05
  - **検討メモ**: Supabase Auth 側の正規化挙動を確認し、サーバー側ユーザー解決の正規化と二重化しない方針を設計時に検討。
  - **確定状態**: 未確定

### 4.5 他システム・通知・受け渡し

  - **背景**: OQ-04 のとおり業務文言は未確定。送信元ドメイン（SPF / DKIM 設定済みか）や Supabase デフォルトテンプレートの利用範囲が影響する。
  - **関連要件**: REQ-101, REQ-104, OQ-04
  - **検討メモ**: 既存運用での送信元設定があるかを確認し、なければインフラ／IaC（terraform）側での設定タスクが派生する可能性を識別。

## 5. 要件から見えたリスクと注意点

- **RISK-01**: 既存 Google OAuth フローへの非互換変更リスク。
  - **関連要件**: REQ-003, US-04
  - **影響**: 既存ユーザーのログイン体験劣化、セッション扱いの不整合。
  - **備考**: 既存 `useOAuthCallback` 周辺の振る舞いを変更せずに拡張できる設計を優先する。

- **RISK-02**: ユーザー同一性の判定漏れによる「同一メールで別人格」が生まれるリスク。
  - **関連要件**: REQ-002, REQ-302
  - **影響**: データ整合性、ユーザーサポート負荷増。
  - **備考**: identity linking の方式選定（TS-101）を早期に確定すべき。

- **RISK-03**: 管理者経路の権限漏洩リスク。
  - **関連要件**: REQ-106
  - **影響**: service_role 鍵相当の権限が漏れた場合の被害が大きい。
  - **備考**: 本番環境では経路自体を閉じる前提を設計時に検討。

- **RISK-04**: 列挙攻撃に対する一貫性（REQ-301 / NFR-101）が、サインアップ・パスワードリセットの応答メッセージにも要求される可能性。
  - **関連要件**: REQ-301, NFR-101
  - **影響**: 部分的にメッセージを区別すると、ログイン経路だけでなくサインアップ／リセット経路からメール存在性が漏れる。
  - **備考**: メッセージ仕様の整合性確認は設計段階で必要。

## 6. 後続の技術設計で確認すべき事項

- **TDQ-01**: identity linking の方式（Supabase の自動 linking 設定 vs 明示 API 呼び出し）。
  - **理由**: REQ-002 / REQ-302 の振る舞いがこれにより変わる。
  - **関連要件**: REQ-002, REQ-302, TI-REF-01
- **TDQ-02**: テストユーザー作成経路の実体（シード／CLI／管理 API）。
  - **理由**: REQ-106 の運用方式が定まらない限り受け入れ確認ができない。
  - **関連要件**: REQ-106, TI-REF-02
- **TDQ-03**: 未確認サインイン試行時の案内メッセージ内容とタイミング（再送 UI はスコープ外で確定）。
  - **理由**: REQ-303 でメッセージのみと確定したが、メッセージ文言と表示タイミングの詳細は設計時に確定する。
  - **関連要件**: REQ-303, TI-REF-03
- **TDQ-04**: Supabase Auth ダッシュボードのパスワードポリシー設定とフロント側バリデーションの実装層整合（ポリシー自体は確定）。
  - **理由**: REQ-101 / REQ-105 の実装で Supabase 側と実装側がずれないようにするため。
  - **関連要件**: TI-REF-04
- **TDQ-05**: ログイン画面 UI の最終構成。
  - **理由**: REQ-001 を満たす画面要素が確定しない。
  - **関連要件**: REQ-001, TI-REF-05
- **TDQ-06**: Google ユーザー向け「パスワード追加」導線の所在。
  - **理由**: REQ-302 の案内文どおりの導線が必要。設定画面側タスクの有無を確認。
  - **関連要件**: REQ-302, OQ-03

## 7. requirements.md との差分メモ

- 本文書は要件を増やしていない。
- 仮説で確定させた事項はない。Supabase Auth の利用は requirements.md の前提条件と一致。
- 「Google ユーザーへのパスワード追加」導線は requirements.md 上では「Google でログインしてから設定画面でパスワード追加」と案内する旨だけを定義しており、設定画面側の実装範囲が別タスクであるかは OQ-03 として残している。
