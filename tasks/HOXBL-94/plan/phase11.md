# Phase 11: E2E テスト + 運用ガイド

## 1. このフェーズの目的

主要な認証フローを Playwright E2E テストで回帰テストとして保護し、テストユーザー作成手順と手動受け入れ検証手順を運用ガイドとして記録する。

## 2. 確認可能なこと

- E2E テスト（サインイン・エラーケース・パスワードリセット UI）がグリーンになること
- `docs/operations/test-user-creation.md` を読んで運用担当がテストユーザーを作成できること（AC-04）
- 既存 E2E テスト（Google OAuth）がグリーンのまま維持されること（REQ-003）
- `docker compose exec e2e npx playwright test` が全体でグリーンになること

## 3. 関連要件・関連設計

- **関連要件**: AC-01〜AC-05, REQ-106, REQ-105, NFR-103
- **関連設計**: §3.5（テストユーザー作成）, §9（リリース計画）

## 4. 依存関係

- **前提フェーズ**: Phase 7（サインイン UI）, Phase 8（サインアップ UI）, Phase 9（ForgotPassword）, Phase 10（ResetPassword）
- **ブロッカー**: DCQ-03（Supabase Auth リダイレクト URL 許可リスト。E2E 環境向けも登録が必要）

- [ ] **TASK-11-01: 運用ガイド作成**
  - **タイプ**: DIRECT
  - **依存タスク**: なし
  - **関連要件**: REQ-106, AC-04
  - **関連設計**: §3.5
  - **実装詳細**:
    - ファイルパス: `docs/operations/test-user-creation.md`
    - Supabase Dashboard でテストユーザーを「確認済み」状態で作成する手順を記載する:
      1. Supabase Dashboard → Authentication → Users → Add user
      2. Email と Password を入力する
      3. `Auto Confirm User` を有効化して作成する
      4. 作成直後から確認メールを経ずにサインイン可能であることを手動確認する（AC-04 の手動受け入れ）
    - 一般のサインアップフォームからは確認メールスキップができないことを記載する（AC-04 の「一般経路からは確認メールスキップ不可」の手動確認手順）
    - NFR-103 の手動確認手順: メールパスワードでサインインしたセッションが Google 認証セッションと同じ保持期間・失効条件であることを Supabase Dashboard の Sessions 画面で確認する
  - **完了条件**: `docs/operations/test-user-creation.md` が作成されていること

- [ ] **TASK-11-02: E2E テスト - サインインと主要エラーケース**
  - **タイプ**: TDD
  - **依存タスク**: TASK-11-01
  - **関連要件**: AC-01, AC-02, REQ-103, REQ-301, REQ-303
  - **関連設計**: §3.2
  - **実装詳細**:
    テストシナリオ:
    - 正常系: Supabase Dashboard で作成した確認済みテストアカウントでサインインしてダッシュボードに遷移できること（AC-01 の手動受け入れを自動化可能な範囲）
    - 誤ったパスワードでサインインを試みると「メールアドレスまたはパスワードが間違っています」が表示されること（REQ-301, AC-02）
    - 存在しないメールアドレスでサインインを試みると同一メッセージが表示されること（NFR-101）
    - 未確認アカウントでサインインを試みると「メールアドレスの確認が必要です」が表示されること（REQ-303）

    **注意**: 確認メールの実際の送受信・クリックを E2E テストで自動化するのは困難なため、「確認済み状態のテストアカウント」（TASK-11-01 の運用ガイドで作成）を使ったサインインフローのみを自動テスト対象とする。
  - **完了条件**: テストシナリオがグリーンになること

- [ ] **TASK-11-04: E2E テスト - パスワードリセット UI**
  - **タイプ**: TDD
  - **依存タスク**: TASK-11-02
  - **関連要件**: AC-03, REQ-104, REQ-105, REQ-305
  - **関連設計**: §3.3
  - **実装詳細**:
    テストシナリオ:
    - `/auth/forgot-password` でメールアドレスを入力して送信すると「パスワードリセットメールを送信しました」が表示されること（REQ-104）
    - 無効なリセットリンク URL を `/auth/reset-password` に付与してアクセスすると「リンクが無効か期限切れです」が表示されること（REQ-305, AC-03 の異常系）
    - REQ-105（旧パスワード拒否）の検証:
      - パスワードリセット完了後に旧パスワードでサインインできなくなること → これは Supabase が `updateUser` 完了時にセッションを失効させることで保証される（§3.3）。E2E テストとして実装するか、または運用ガイドの手動確認手順として記録する

    **注意**: パスワードリセットメールの実際の受信とリンクのクリックを E2E テストで自動化するのは困難なため、UI の表示確認（成功メッセージ・エラーケース）のみを自動テスト対象とする。REQ-105 の旧パスワード拒否は TASK-11-01 の運用ガイドに手動確認手順を記載する。
  - **完了条件**: テストシナリオがグリーンになること
