## 目的

`@knowledge/` に蓄積されたナレッジは、時間の経過やコード変更によって陳腐化する。また、単発のトラブルシュート記録ではなく、プロジェクト全体で繰り返し参照すべき原則は `CLAUDE.md` / `.claude/rules/*.md` に昇格させたほうが価値が高い。このスキルは、ナレッジの棚卸し・陳腐化対応・ルール昇格・重複整理までを一連の流れでおこなう。

各フェーズの間で必ずユーザーに報告し、承認を得てから次のフェーズへ進むこと。ユーザーの指示なしに先読みしてまとめて実行しない。

## 事前確認

`@knowledge/` 配下のカテゴリディレクトリ（例: `auth`, `backend`, `e2e`, `frontend`）を列挙する。ファイルが1件も存在しない場合、その旨をユーザーに伝えて待機する。

## 実行内容

### フェーズ1: 棚卸し（並列調査）

カテゴリ（サブディレクトリ）ごとに **Explore サブエージェント（haikuなど軽量モデルを指定）** を並列起動する。CLAUDE.mdの「ファイル探索のExploreサブエージェントは軽量モデルを選択する」方針に従う。

各サブエージェントに伝える内容:
- 対象ナレッジファイルのパス一覧（1カテゴリにつき1〜複数エージェント。ファイル数が多い場合はカテゴリをさらに分割してもよい）
- リポジトリ構成の要点（バックエンド/フロントエンドの技術スタック、Docker Compose構成、WORKDIRなど、判断に必要な最小限の文脈）
- 調査内容:
  1. ナレッジが言及する具体的なコード・設定・ファイルパス・関数名が、現在のリポジトリに実在するか grep/Read で裏付けを取る
  2. 言及されたコードがすでに変更・削除・リファクタリングされていて、記載内容と現状が食い違っていないか確認する
  3. 内容が今も再発防止・学習の価値を持つか判断する（恒久対応済みで再発し得ないものは価値が低いと判断する）
- 読み取り専用でおこない、ファイルは変更しないことを明示する
- 報告フォーマット: ファイル名 / 状態（`最新` / `一部陳腐化` / `完全に陳腐化` / `不要（恒久対応済みで再発防止価値が低い）`）/ 根拠（具体的なコード引用）/ 推奨アクション（残す・更新する・削除する）
- 語数上限を指定し、簡潔な報告を求める

全カテゴリの完了通知を受け取ったら、メインエージェントが1つの表に統合し、ユーザーに報告して待機する。

### フェーズ2: 陳腐化への対応

ユーザーの承認を得てから実施する。

- **完全に陳腐化 / 不要と判定されたファイル**: 削除する
- **一部陳腐化と判定されたファイル**: 該当箇所について実装コードを自分で再確認し、記載内容を現状に合わせて書き換える
  - **禁止**: 「〜のため変更」「〜によって古くなり〜」のような変更理由・経緯を残す記載
  - あたかも最初からその内容だったかのように、現状に即した記述へ書き換える

対応内容をユーザーに報告して待機する。

### フェーズ3: ルール昇格の判断

フェーズ1で「残す」判定になったファイル（新規に記録されたナレッジを含めてもよい）を対象に、ルールへの昇格余地を検討する。

- 対象ドメインに対応する `.claude/rules/*.md`（`backend.md` / `frontend.md` / `e2e.md` / `schema-db.md` / `documents.md` / `design-system.md` など）を実際に Read/grep し、内容がすでに反映されているかどうかを自分で裏取りする
  - **重要**: 過去のサブエージェント報告やナレッジ自身の記述を鵜呑みにしない。「既にルールに書かれている」という主張も実際にファイルを開いて確認する
- 判定基準:
  - **昇格候補**: 汎用化可能で、今後も別の実装で繰り返し発生・参照されうる原則・設計判断・コーディング規約
  - **非候補**: 単発のインシデント記録、既にルールに反映済み、適用範囲が狭すぎるもの・再発可能性が低いもの
- 候補と非候補を理由付きで表にまとめ、ユーザーに提示して待機する（この時点ではファイルを変更しない）

### フェーズ4: 反映とナレッジ整理

ユーザーの承認を得てから実施する。

1. 該当する `.claude/rules/*.md` に、既存の書式・粒度に合わせて簡潔な原則を追記する
2. 昇格した内容と元のナレッジファイルの重複度を確認し、以下のいずれかで整理する
   - 内容の主眼が昇格した原則そのもの（固有の実装コード例に乏しい） → **ファイルごと削除**
   - 固有の実装レシピ・コード例・トラブルシュート手順が残り、ルールの箇条書きだけでは表現しきれない → **原則と重複する記述（「学び」の該当箇所など）のみ削除**し、レシピ部分は保持する
3. 対応内容をユーザーに報告して待機する。

## 出力フォーマット例

### フェーズ1完了時

```md
## ナレッジ陳腐化調査 総合報告

### {カテゴリ名}（n件）
| ファイル | 状態 | 詳細 |
|---|---|---|
| `xxx.md` | 最新 / 一部陳腐化 / 完全に陳腐化 / 不要 | 根拠と推奨アクション |
```

### フェーズ3完了時

```md
昇格候補: {ファイル名} → {昇格先ルールファイル}（理由）
非候補: {ファイル名}（理由）
```

いずれのフェーズも、報告の末尾で次の対応（削除・更新・昇格）についてユーザーの判断を仰ぎ、承認なしに実行しない。
