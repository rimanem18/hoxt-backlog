## タスク実施

提示されたタスクファイルを読み込んで、実施してください。

- ユーザーから requirement_number/ID が提示されない場合、自己判断で進めずに、ユーザーに指示を仰いでください。
- タスク計画はあくまで計画です。CLAUDE.md や ガイドラインおよび実装と突合したときに不自然な箇所がある場合は差異を記録した上、強引に計画に沿うのではなく合致を優先してください。

## タスクの理解

まずは以下のディレクトリに存在するファイルを読んで理解してください。

- `@tasks/{requirement_number/ID}/plan/`
  - overview.md
  - 提示された phase{number}.md の直前の phase{number}.md（存在する場合）
    - 並行で実装が進行している可能性も考慮する
  - 提示された phase{number}.md
- `@tasks/{requirement_number/ID}/spec/` から関連記述を探して読む
- `@tasks/{requirement_number/ID}/technical/` から関連記述を探して読む

## 開始時刻の確認と記録

- 開始前に、date コマンドで日時を JST で出力し、開始時刻を記録してください。
  - 途中で Compaction が入って開始時刻が不明になる可能性があるため、最初にタスク計画ファイルに書き込みます。

## 状況分析

- git log/diff を確認して、前 phase で明示されていない変更も把握します。
  - 変更の内容を理解して、今回の実装に影響があるか分析します。
- 並行で Explore サブエージェントも起動し、コードベース調査を依頼します。
  - Explore サブエージェントから得られた情報も踏まえて、実装方針を検討します。

## ナレッジの確認

作業に着手する前に、今回担当するフェーズに関連しそうなナレッジを `@knowledge/` から確認します。別のセッションで作成された知見が蓄積されている可能性があります。knowledge にはフロントマターがあるものもあるため、まずは必要かどうかそこで見極めて読みます。

## 実行内容

プランの実行は1フェーズ単位で実施して、自己判断で次のフェーズに進行はしないでください:

1. Red - Green - Refactor のサイクルで実装します。ただし、「TDD が適さないタスクである」と判断した場合は、DIRECT に実装して OK です。
  - Green を実装するサブエージェントは以下から内容の重みに応じて選択します
    - @green-haiku-worker
    - @green-minimal-implementer

2. Code-review サブエージェントにレビューを依頼してください。このとき、以下を伝えてください。

- レビューの観点を明確に伝えるための変更内容とレビューしてほしいポイント
- メインエージェントで十分なテストをしているため、ビルドやテストはせずにコードベースのレビューをしてほしい旨
- 異常系・境界値テストが不足していないか
- 言語やフレームワークの慣習や流儀に従えているか。もしも齟齬がある場合、プロジェクトが提示するガイドラインがそもそもおかしくないか確認し、ガイドラインがおかしい場合は修正案を提示してほしい旨

3. その後、 `/resolve-feedback` Skill を使用してください。妥当性の高い指摘があるか確認します。

- Yes -> 改善する
- No -> ユーザーに成果物の確認を促す。

4. Code-review サブエージェントを待つ間、テストやリントと型チェック、docker compose exec {コンテナ名} build によるビルドチェックおよび静的セキュリティチェックを実施してください。これらは @quality-gate-runner サブエージェントに依頼してください。

5. レビュー後の改善に関して 対応に完全は求めていない。（原則、成果60%程度で承認）:

- **対応必須**: 機能が壊れていたら修正
- **対応推奨**: 不要なコードの削除
- **対応推奨**: 実施時間に見合った提案の取り入れ
- **対応任意**: 必要最低限の Why のコメント記載
- **対応非推奨**: 実施時間に見合わない品質向上
- **対応禁止**: ついでに機能を追加

6. サブエージェントたちの行動が終わったら、最後に `make fmt` を実施します。
7. タスクのチェックをしてください。

- 作業を完了した範囲のみタスクのチェックボックスを埋めて、進捗状況を管理してください。
- タスクファイルを読み直してください。今回の実装によってタスク管理ファイルの変更の必要性があるか確認し、修正が必要と判断した場合は、ユーザーに指示を仰いでください。
- やむを得ずスキップしたり事前策定した設計と異なる対応をした内容があればタスク管理ファイルの末尾に記載してください。
- typecheck / test / lint / build にかかった時間を末尾に記録してください。

## 実装完了後の記録

- date コマンドで日時を JST で出力し、終了時刻とこのフェーズの実装にかかった合計時間を記録してください。
- 合計時間の計算には、`diff_minutes` を使用してください。

## コミット

```md
## 差異の記録

{差異を記載する}
```

実装を終えて成果物の確認を促す際はサマリーを出力し、コミットを促してください。
{issue_number} はブランチ名に含まれています。含まれていない場合は、ユーザーに指示を促してください。

### 出力フォーマット例

```md
phase1 の実装が完了しました。

実装サマリー:
{実装サマリーを出力}

差異の記録:
{事前定義された設計との差異のサマリーとそれをタスクファイルに記録したかどうか（設計と異なる対応をした場合）}

ナレッジ: あり（エラー解決などをした場合）
コミット後、`/knowledge` の実行を推奨します。

--- コミットメッセージ: ---
feat: Redux状態管理を実装 {requirement_number/ID}

- Redux Toolkitでストアを設定
- 型付きhooks（useAppDispatch、useAppSelector）を実装
- TODOスライスを実装

---

上記の内容でコミットしますか？(y/n)
※コミットを承認する前に、必ずユーザー自身でファイル差分を確認して、レビューしてください。
```

y の入力、またはそれに類する承認のメッセージがあれば、 `git add` と `git commit` を実施してください。
ただし、関連性の低い変更が一つのコミットに含まれないように、適切に分割する必要があります。その際は複数回にわけてください。

また、エラー解決などをした場合、今回のセッションで新たに得た学びや気づきをナレッジとして記録してください。ナレッジを蓄積させることで、別のセッションの agent が参照できるようにすることが目的です。
