# 出力形式（requirements.md / technical-spec.md）

以下の形式で要件定義の成果物を作成してください。

- 具体的なディレクトリ構成や具体的なコード例は記載しないでください
- 実装方法ではなく、要件・責務・制約を記載してください
- 曖昧な表現を避け、テスト可能な表現にしてください
- 1 要件 1 意味で記載してください
- 各要件には「根拠」と「確定状態」を付与してください
- 不明点は推測で埋めず、未決事項に記載してください
- 技術設計の判断が必要な内容は requirements.md で確定させず、technical-spec.md に整理してください
- 受け入れ基準には、関連するユーザーストーリーと要件を必ず紐付けてください

---

# 2. technical-spec.md の出力形式

technical-spec.md は、要件定義の結果から見えた技術設計上の検討論点を整理するための補助文書です。

この文書は、技術方式を確定するための最終設計書ではありません。後続の技術設計スキルや設計レビューの入力として利用してください。

```md
# {機能名} 技術設計メモ

## 1. 目的

- **Requirement ID**: {requirement_number}
- **参照要件書**: tasks/{requirement_number}/spec/requirements.md
- **目的**: {requirements.md を補完し、後続の技術設計で見落としやすい論点を整理する}
- **位置づけ**: {設計の正本ではなく、技術検討の補助メモであることを明記}

## 2. 前提

- requirements.md の内容を正本として扱う
- この文書では、技術方式を断定しない
- 未確定な論点は、未確定のまま明示する
- 要件と矛盾する内容を書かない

## 3. 参照すべき要件サマリー

- **関連ユーザーストーリー**: {US-xx, US-yy}
- **関連受け入れ基準**: {AC-xx, AC-yy}
- **関連要件**: {REQ-xxx, REQ-yyy}
- **関連未決事項**: {OQ-xx, OQ-yy}

## 4. 技術的に考慮すべき論点

### 4.3 権限・公開範囲

### 4.4 入出力・バリデーション
```

# 3. 出力後に必ず示すサマリー

実行後には、本文とは別に最低限以下を報告してください。

- 対象機能に関連して確認した既存情報のサマリー
- ヒアリング結果の要約
- 既存仕様・既存運用との差分
- 今回のスコープとスコープ外
- 未決事項の件数
- technical-spec.md に記録した技術検討メモの件数
- 作成したファイルのパス
- 要件数、受け入れ基準数、ユーザーストーリー数

また、未確認事項や「仮置き」の要件がある場合は、レビューを促してください。

---

# 4. 後続の技術設計スキルとの接続

後続の技術設計スキルは、少なくとも以下を前提にしてください。

- requirements.md を業務要件の正本として扱う
- technical-spec.md を技術検討の補助入力として扱う
- technical-spec.md に書かれている内容を、そのまま確定設計として扱わない
- requirements.md と technical-spec.md に矛盾がある場合は、requirements.md を優先し、必要に応じて確認事項として返す
