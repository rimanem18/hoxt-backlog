成果物は不必要に長くしないでください。

簡潔さよりも、要件の完全性、一貫性、検証可能性を優先してください。

ただし、同じ要件の言い換え、重複した説明、一般論、
内容のない前置きやまとめによる水増しは避けてください。

各要件は、原則として1つの振る舞いだけを記述してください。
各要件に一意のIDを付け、指定されたEARS形式を厳密に使用してください。

要件として確定していない内容を推測で追加しないでください。
不明点は「仮定」「未決事項」「確認事項」として要件本文から分離してください。

要件の意味を正確にするために必要な条件、トリガー、状態、
期待される応答、例外は省略しないでください。

# 目的

対象機能 1 件について、既存情報とユーザーへのヒアリング結果をもとに、EARS（Easy Approach to Requirements Syntax）を用いた要件定義書を作成してください。

このスキルの主目的は、ステークホルダーから業務要件を引き出し、実装・レビュー・テストに利用できる粒度で整理することです。

また、要件定義の過程で見えてきた技術的な検討論点は、要件本文に混ぜず、後続の技術設計で参照できるメモとして technical-spec.md に分離してください。

# このスキルの対象ユーザー

このスキルは、主に以下のようなステークホルダーへのヒアリングを前提とします。

- 業務担当者
- プロダクトオーナー
- 依頼者
- 現場運用担当
- カスタマーサポート担当
- ドメイン知識を持つ関係者

# このスキルで作成する成果物

このスキルは、以下の 3 ファイルを作成します。

- tasks/{requirement_number}/spec/requirements.md
- tasks/{requirement_number}/spec/technical-spec.md
- tasks/{requirement_number}/spec/interview.md

## requirements.md の役割

- 業務要件を明確にする
- 対象・対象外を明確にする
- EARS 形式でテスト可能な機能要件を記述する
- 受け入れ基準、未決事項、差分を整理する

## technical-spec.md の役割

- ヒアリング結果から見えた技術設計上の論点を整理する
- ただし、技術方式を確定しない
- 後続の技術設計スキルが論点を見落とさないためのメモとして扱う

## interview.md の役割

- ユーザーへのヒアリング内容を記録する
- ヒアリングの質問と回答を整理する
- どのような質問があったのか、どのような回答があったのかを後から参照できるようにする

# このスキルで扱わないこと

以下は、このスキルのヒアリング対象外とします。

- API 仕様の詳細設計
- DB テーブル設計、カラム設計
- クラス設計、モジュール設計
- フレームワークやライブラリの選定
- インフラ構成、ネットワーク構成
- 監視方式やジョブ実装方式の詳細
- 画面部品や UI 実装方法の具体設計
- 実装工数の見積もり
- 技術的負債の解消方針そのもの

これらが論点として必要になった場合は、ユーザーに設計判断を求めず、technical-spec.md に記録し、後続の技術設計で扱ってください。

# 完成物の品質基準

作成する文書は、単に文章量が多いものではなく、以下を満たすものとしてください。

- 曖昧でない
- 1 要件 1 意味である
- テスト可能である
- 正常系だけでなく異常系も含む
- スコープ内外が明確である
- 根拠が追跡できる
- 不明点を推測で埋めず、未決事項として管理できる
- 技術設計と業務要件が混在していない

# 基本方針

- EARS は機能要件の記述に使用する
- EARS で要件文を書くだけでは、要件定義書が完成したとはみなさない
- 必要に応じて、スコープ、用語、ユーザー、業務ルール、入力と結果、例外条件、受け入れ基準、未決事項を含める
- 実装方法ではなく、システムの責務と振る舞いを記述する
- ヒアリング対象は非技術系ステークホルダーを想定し、業務目的・利用条件・期待結果・例外条件を中心に確認する
- 技術的な設計、実装方式、内部構造、データベース設計、API 詳細は確認しない
- 技術的な前提が必要になった場合は、ユーザーに設計判断を求めず、未決事項または technical-spec.md に分離する
- システム内部の仕組みではなく、外から観測できる責務と振る舞いを記述する
- 既存情報の確認は、対象機能に関係する範囲に限定する
- 調査できていない情報は「未確認」として扱う
- 不明点は推測で補完せず、ヒアリング事項または未決事項として残す
- 非機能要件は、業務上または運用上の要請として説明可能なものだけを扱う
- ユーザーストーリー、要件、受け入れ基準は相互に関連付ける
- UI の見た目と業務上の責務を混同しない
- 既存仕様と既存の利用実態に差分がある場合は、その差分を明示する

# 入力が不足している場合のルール

以下が不足している場合は、自己判断で作成を開始せず、必ずユーザーに確認してください。

- requirement_number
- 対象機能の概要
- 受け入れ基準、または達成したい成果
- 主な利用者、または想定ユーザー

ただし、軽微な表現揺れは吸収して構いません。

# ヒアリング時の禁止事項

以下のような質問はしないでください。

- API は必要ですか
- DB に何を保存しますか
- テーブルはどう分けますか
- どのイベントで非同期実行しますか
- バックエンドでバリデーションしますか
- 権限はロールベースですか属性ベースですか
- 監査ログはどの粒度で実装しますか
- 外部連携は同期ですか非同期ですか
- どの技術スタックで実装しますか

代わりに、以下のように業務上の期待結果として聞いてください。

- 誰がこの機能を使いますか
- どのような場面で使いますか
- 何が起きたら処理を開始すべきですか
- 成功したとき、利用者は何を確認できれば十分ですか
- 失敗したとき、利用者には何を伝える必要がありますか
- 誰には見えて、誰には見えないべきですか
- 他の部署や仕組みへの連絡・受け渡しは必要ですか

# 進め方

## Phase 0. 入力内容の整理

まず、ユーザーの入力から以下を整理してください。

- requirement_number
- 機能名または対象機能
- ユーザーストーリー
- 既存の受け入れ基準
- 明示されている制約
- 明示されているスコープ外
- 不明点

不足があれば、まとめて大量に聞かず、一問一答形式で確認してください。

## Phase 1. 関連範囲の確認

対象機能に直接関係する範囲だけを確認してください。

確認対象の例:

- 関連する既存仕様
- 関連する業務ルール
- 関連する画面や帳票など、ユーザーが認識している振る舞い
- 関連する既存の受け入れ基準やバックログ記述
- 関連する運用フロー
- 関連する用語定義
- 関連する権限の業務上の違い
- 関連する通知や他部門・他システムとの業務上の受け渡し

確認時のルール:

- 「網羅的に」ではなく「対象機能に関連する範囲に限定して」確認する
- ユーザーから見える事実と、内部実装の推定を分ける
- 実装方法の推測はしない
- 既存仕様と現行の利用実態に差分がある場合は、その差分を明示する
- 技術的な詳細が必要な場合は、未確認または後続の技術設計で確認として扱う

## Phase 2. ヒアリング

確認結果を踏まえて、要件化に必要な不足情報をユーザーに確認してください。

優先して確認する観点:

- 主な利用者
- 業務上の目的
- 利用する場面
- きっかけとなる操作や出来事
- 成功したといえる結果
- 失敗・例外として扱う条件
- 入力が必要な情報
- 出力として必要な結果や通知
- 閲覧・操作できる人の違い
- 他部門や他システムとの受け渡しの有無
- 今回やること / やらないこと
- 既存運用や既存ルールとの違い
- 未決事項として残すべき論点

ヒアリング時のルール:

- 1 回で全部聞かない
- 非技術系ステークホルダーが答えにくい技術的な質問はしない
- 実装方法を前提に質問しない
- 曖昧な語をそのまま採用しない
- 「適切に」「必要に応じて」「高速に」などの曖昧表現は、業務上の判断基準に言い換えるため確認する
- 技術判断が必要な論点は、ユーザーに決めさせず、未決事項または technical-spec.md に残す

## Phase 3. スコープ整理

今回のタスクで以下を明確にしてください。

- 今回やること
- 今回やらないこと
- 既存バックログとの関係
- 依存する別タスク
- 先送りする論点
- 要確認の論点

品質低下を招かない範囲で、今回の対象を最小化してください。

## Phase 4. requirements.md の作成

要件定義書を tasks/{requirement_number}/spec/requirements.md として作成してください。

作成時の必須ルール:

- 1 要件 1 意味にする
- 1 つの要件文に複数の振る舞いを詰め込まない
- 実装方法や具体コードではなく、システムの責務を書く
- UI 表現と業務責務を混同しない
- 受け入れ基準から直接テスト観点が引けるようにする
- 正常系だけでなく異常系・境界値も含める
- 各要件に根拠と確定状態を付与する
- 推測で補った内容は「仮置き」とし、必要に応じて補足を書く
- 不明点は未決事項に残す
- 技術設計に属する論点は requirements.md に書き込まず、必要に応じて technical-spec.md に移す

## Phase 5. technical-spec.md の作成

requirements.md の作成後、ヒアリング結果および未決事項をもとに、tasks/{requirement_number}/spec/technical-spec.md を作成してください。

technical-spec.md の目的は、後続の技術設計スキルが requirements.md を読んだだけでは見落としうる技術検討論点を整理することです。

記載してよい内容:

- 要件から見えている技術的な論点
- 要件実現にあたり考慮が必要なシステム境界
- 状態管理、権限制御、監査、整合性、通知、連携などの検討ポイント
- 要件上は未確定だが、技術設計で判断が必要になる可能性が高い事項
- requirements.md の各要件に対応する技術検討メモ

記載してはいけない内容:

- 技術方式の断定
- 採用技術の決定
- API や DB の詳細仕様の確定
- 実装計画の断定

作成時のルール:

- technical-spec.md は、要件本文の代替ではなく補助メモとして扱う
- requirements.md と矛盾しないこと
- 憶測だけで詳細化しないこと
- 「検討が必要」「選択肢がある」「確認が必要」を明確に書くこと
- requirements.md の要件 ID、受け入れ基準 ID、未決事項 ID と対応付けることが望ましい

## Phase 6. interview.md の作成

ヒアリングの質問と回答を整理し、tasks/{requirement_number}/spec/interview.md として記録してください。

# EARS の書き方ルール

機能要件は、以下の分類を原則として使用してください。

- 常時要件（Ubiquitous）
- イベント駆動要件（Event-driven）
- 状態依存要件（State-driven）
- 異常系要件（Unwanted behavior）
- 任意機能要件（Optional feature）
- 複合要件（Complex）

記述ルール:

- 1 要件 1 意味
- 主語、条件、システムの振る舞いを明確にする
- 曖昧語を避ける
- 実装詳細を書かない
- テスト可能にする
- 可能な限り受け入れ基準と対応付ける

避ける表現の例:

- 適切に表示する
- 必要に応じて通知する
- ユーザーフレンドリーにする
- 高速に動作する
- 可能であれば保存する

# 根拠と確定状態のルール

各要件には最低限以下を持たせてください。

## 根拠

次のいずれか、または複数を記載してください。

- ヒアリング
- 既存仕様
- 既存運用
- 業務ルール
- 法令・規約
- ベストプラクティス
- 仮定

## 確定状態

次のいずれかを記載してください。

- 確定: ユーザー確認済み、または根拠が明確
- 仮置き: 妥当な補完だが未確認
- 未確定: 要確認

必要に応じて補足を付けてください。

# 非機能要件の扱い

非機能要件は、業務上または運用上の要請として明示されているものだけを扱ってください。

以下のような場合に限り確認してください。

- 明確な応答時間や処理時間の期待がある
- 法令・規約・監査上の制約がある
- データ保持期間や削除ルールが決まっている
- 利用者や運用担当が明示的に必要だと述べている

技術方式の選定が必要な観点は、このスキルでは確定させず、technical-spec.md に分離してください。

# 実行後の確認

最後に必ず以下を示してください。

- 対象機能に関連して確認した既存情報のサマリー
- ヒアリング結果の要約
- 既存仕様・既存運用との差分
- 今回のスコープとスコープ外
- 未決事項の件数
- technical-spec.md に記録した技術検討メモの件数
- 作成したファイルのパス
- 要件数、受け入れ基準数、ユーザーストーリー数

また、未確認事項や「仮置き」の要件がある場合は、ユーザーにレビューを促してください。

# 後続スキルとの接続方針

後続の技術設計スキルは、requirements.md と technical-spec.md を入力として扱うことを前提にしてください。

requirements.md は業務要件の正本、technical-spec.md は技術設計上の補助メモとして扱い、両者を混同しないでください。
