# 目的

承認済みの要件定義書 requirements.md と技術設計書 technical-design.md をもとに、対象機能 1 件について実装可能なタスク計画を作成してください。

このスキルの主目的は、要件と設計を満たすための実装作業を、ワンショット単位のタスクと 4 時間単位のフェーズに分解し、実行順と依存関係が明確な計画へ落とし込むことです。

各フェーズは、利用者または呼び出し元から見て意味のある機能成果を持つ垂直スライスとして設計してください。

# このスキルの入力と位置づけ

このスキルは、要件定義スキルと技術設計スキルの後続として使用します。

## 正本として扱う入力

- tasks/{requirement_number}/spec/requirements.md
- tasks/{requirement_number}/technical/design.md

## 補助入力として扱うもの

- tasks/{requirement_number}/spec/technical-spec.md
- tasks/{requirement_number}/technical/dataflow.md
- tasks/{requirement_number}/technical/api-design.md
- tasks/{requirement_number}/technical/data-model.md
- 関連する既存実装
- 関連する開発ルール、技術スタック定義

## 入力の優先順位

内容が矛盾する場合は、以下の優先順位で扱ってください。

1. requirements.md
2. technical-design.md
3. technical-design.md に明示された設計前提・確認結果
4. 補助設計文書（dataflow.md, api-design.md, data-model.md など）
5. technical-spec.md
6. 既存実装
7. 一般的なベストプラクティス

requirements.md と technical-design.md に矛盾がある場合は、requirements.md を優先し、設計差分として明示してください。

# このスキルの成果物

このスキルは、最低限以下を作成します。

- tasks/{requirement_number}/plan/overview.md
- tasks/{requirement_number}/plan/phase1.md
- tasks/{requirement_number}/plan/phase2.md
  - フェーズ数に応じて継続

ただし、タスク実行に直接寄与しない補助文書は無理に作成しないでください。

# このスキルで扱うこと

- 要件と技術設計に対応するユースケースの洗い出し
- 実装順序と依存関係の整理
- フェーズ単位の機能成果の定義
- ワンショット単位の実装タスクへの分解
- 各タスクの完了条件、テスト観点、依存関係の明示
- 垂直スライスを維持したフェーズ設計
- リスクの高いタスクや未確定事項の明示
- 実装前に確認すべき事項の整理

# このスキルで扱わないこと

以下は、このスキルの主目的ではありません。

- 業務要件の再定義
- 技術設計の再設計
- 実装コードの作成
- 工数見積もりの厳密化
- チーム編成や担当者のアサイン
- チケットシステムへの登録作業そのもの

要件や設計に不足や矛盾がある場合は、タスクに押し込まず、確認事項や前提として明示してください。

# 完成物の品質基準

作成するタスク計画は、以下を満たすものとしてください。

- requirements.md の主要要件と technical-design.md の主要設計項目にトレーサブルである
- 各フェーズが利用者または呼び出し元にとって意味のある成果になっている
- 各フェーズが可能な限り 4 時間以内で完了可能な粒度である
- 4 時間を超える場合は分割されている
- 同じフェーズ内で追加した主要コードが利用またはテストされる前提になっている
- レイヤごとの横割りではなく、機能断面の縦割りである
- 異常系、境界条件、UI/UX 補助要件、テスト観点が落ちていない
- 後続フェーズのためだけの準備作業に偏っていない
- 未確定事項や高リスク箇所が明示されている

# 基本方針

- requirements.md を業務要件の正本として扱う
- technical-design.md を実装計画の主要設計入力として扱う
- technical-spec.md は補助情報として扱い、正本に優先しない
- フェーズは domain / repository / usecase / handler / frontend / backend などの実装レイヤ単位ではなく、機能成果単位で分割する
- 各フェーズは可能な限り 1 つのユースケース、または 1 つの細い end-to-end を完結させる
- backend / frontend / test はカテゴリとして先に分離せず、各ユースケースを実現する内部タスクとして内包する
- 同じフェーズで作成したメソッド、クラス、コンポーネント、API、UI は、そのフェーズ内で利用または検証される状態にする
- 後続フェーズのためだけの抽象化、共通化、インターフェース追加、事前準備は原則行わない
- walking skeleton が必要な場合でも、最小限の動作確認ができる状態に限る
- 大きなリファクタリングは無理に同一フェーズへ押し込まず、独立タスクとして明示する
- 既存実装や既存設計との整合性を踏まえ、自然な変更単位で分割する
- 確認事項は、タスクに変換せず前提またはブロッカーとして明示する

# 入力が不足している場合のルール

以下が不足している場合は、自己判断でタスク分解を開始せず、必ずユーザーに確認してください。

- requirement_number
- requirements.md
- technical-design.md

requirements.md が存在しない場合は、要件定義スキルの完了を促してください。
technical-design.md が存在しない場合は、技術設計スキルの完了を促してください。

# ユーザーへの確認方針

このスキルでは、以下のような実装詳細をむやみに質問しないでください。

- 実装順序を frontend 先行にするか backend 先行にするか
- どのテストフレームワークを使うか
- ORM やライブラリをどれにするか
- コンポーネント分割を何ファイルにするか

これらは technical-design.md と既存実装を踏まえて計画側で自然に決めてください。

代わりに、以下のような計画成立上の確認事項だけを必要に応じて質問してください。

- 先に実装すべき優先ユースケースはどれか
- 初回リリースに含める範囲はどこまでか
- 一時的にスコープ外へ出してよい機能はあるか
- デモ可能性を優先するか、内部品質を優先するか
- 互換性維持のために分割が必要な導入手順があるか

# 進め方

## Phase 0. 入力内容の整理

まず、ユーザーの入力から以下を整理してください。

- requirement_number
- 対象機能名
- requirements.md の有無
- technical-design.md の有無
- 補助設計文書の有無
- 既存実装の参照要否
- 優先度やリリース範囲に関する希望
- 不明点

不足があれば、計画成立に必要なものだけを一問一答形式で確認してください。

## Phase 1. 要件・設計の読解

対象機能に直接関係する範囲だけを確認してください。

確認対象の例:

- requirements.md のユーザーストーリー、受け入れ基準、要件
- technical-design.md の設計方針、責務分割、処理フロー、データモデル、インターフェース設計、リスク
- 補助設計文書にあるフロー図、API 契約、データ制約
- 既存実装にある流用可能な構造

確認時のルール:

- まず requirements.md から利用者価値と成功条件を抽出する
- 次に technical-design.md から実装責務と設計上の制約を抽出する
- 実装上の複雑性やリスクが高い箇所を特定する
- requirements.md と technical-design.md の差分がある場合は、そのままタスク化せず確認事項として扱う

## Phase 2. ユースケースの洗い出し

要件定義書と技術設計書をもとに、まず以下を整理してください。

- 利用者または外部システムから見える操作
- その操作によって得られる結果
- 正常系
- 異常系
- UI/UX 上の補助要件
  - ローディング状態
  - エラー表示
  - 空状態
  - モバイル対応
  - アクセシビリティ要件

- 技術設計上、同時に実装しないと成立しない内部要素

この段階では、バックエンドタスク / フロントエンドタスク / E2E タスクのようにレイヤ別には分解しないでください。

## Phase 3. 依存関係の分析

以下を整理してください。

- ユースケース間の依存関係
- 並行実行可能なユースケース
- クリティカルパス
- 先に用意すべき最小限の walking skeleton の有無
- 既存実装への影響範囲
- リリースリスクや移行リスク

依存関係がある場合でも、可能な限り価値のある最小単位の垂直スライスに分割してください。

レイヤ順に実装する前提でフェーズを並べないでください。

## Phase 4. タスクの詳細化

各フェーズ内の各タスクに以下を含めてください。

- タスク名
- タスクタイプ（TDD / DIRECT）
  - TDD: コーディング、ビジネスロジック実装、UI 実装、テスト実装など開発作業
  - DIRECT: 環境構築、設定変更、データ移行準備、ドキュメント更新、確認作業など準備作業

- 関連要件
- 関連設計項目
- 依存タスク
- 実装詳細
- 完了条件
- 単体テスト要件
- 統合テスト要件
- UI/UX 要件（該当する場合）
  - ローディング状態
  - エラー表示
  - 空状態
  - モバイル対応
  - アクセシビリティ要件

- リスクまたは注意点（必要な場合）

補足:

- フェーズの主語は機能成果にする
- レイヤ単位の作業は、フェーズの内部タスクとして整理する
- 例えば domain, repository, usecase, handler, frontend, test は、必要なら同一フェーズ内のサブタスクとして含める
- そのフェーズ単体でデモ可能か、または呼び出し元視点で確認可能かを必ず意識する

## Phase 5. フェーズ分割

- 各タスクをワンショット単位の粒度で設計する
- タスクを 4 時間単位のフェーズに分割する
- 4 時間を超えるようなフェーズは分割する
- 各フェーズは、利用者または呼び出し元から見て意味のある 1 つの機能断面を完成させる
- 各フェーズは、可能な限り完了後にデモ可能または動作確認可能な状態とする
- 1 フェーズ内に、その機能断面に必要な backend / frontend / test を含める
- 別フェーズで使用予定のメソッドやクラスなどの事前準備を避ける
- 後続フェーズを見越した過剰な抽象化、共通化、インターフェース分離を避ける
- repository のみ、handler のみ、frontend のみ、test のみのようなレイヤ単独フェーズは禁止する
- ただし、複数ユースケースの前提となる最小限の walking skeleton は独立フェーズとして許可する
- その場合も、最小限の動作確認が可能な状態を作ること

## Phase 6. ファイル作成

ファイルが存在する場合、内容を上書きしてください。

- tasks/{requirement_number}/plan/overview.md
- tasks/{requirement_number}/plan/phase1.md
- tasks/{requirement_number}/plan/phase2.md
  - フェーズ数に応じて継続

作成ルール:

- 各フェーズごとに個別のタスクファイルを日本語で作成する
- 各タスクにチェックボックスを追加して完了状況を追跡可能にする
- 各タスクには機能名またはその簡潔な要約を含める
- overview.md では、各フェーズの機能成果と依存関係が分かるようにする
- phase ファイルでは、フェーズ内タスクと完了条件が分かるようにする

## Phase 7. 計画品質の点検

作成後、客観的評価を得るためサブエージェントに依頼して、最低限以下を点検してください。自己点検は禁止します。

- タスクをこなすことで要件を満たすことができるようになっているか
- 主要な要件と設計項目がフェーズへ落ちているか
- 各フェーズが垂直スライスになっているか
- レイヤごとの横割りになっていないか
- 4 時間を超えるフェーズが残っていないか
- 異常系やテスト観点が抜けていないか
- 未確定事項をタスクとして誤魔化していないか
- 既存実装との整合性を崩す危険が高い変更が明示されているか

# フェーズ設計ルール

## 良いフェーズの条件

- フェーズ完了後に、利用者または呼び出し元から見た成果を説明できる
- フェーズ完了後に、最低限の動作確認またはデモができる
- そのフェーズで追加した主要なコードが、同じフェーズ内で利用またはテストされる
- 後続フェーズのための準備だけで終わっていない
- 必要であれば backend / frontend / test をまたいでいてもよい
- 主要な要件と設計項目に対応付けられる

## 悪いフェーズの例

- ドメインモデルだけ追加するフェーズ
- repository だけ実装するフェーズ
- usecase だけ作って呼び出し元がないフェーズ
- handler だけ作って UI や呼び出し確認がないフェーズ
- frontend の見た目だけ作って API 接続がないフェーズ
- 将来使うためだけの抽象化や共通化を行うフェーズ

# 推奨する出力観点

## overview.md

- 各フェーズの目的を機能成果ベースで簡潔にまとめる
- フェーズ間依存を明示する
- 各フェーズについて、何が確認可能になるかを書く
- 関連要件と関連設計項目を簡潔に示す
- レイヤ別の進捗ではなく、機能の進捗が分かるようにする

## phaseN.md

各 phase ファイルでは、必要に応じて以下の観点で内部タスクを整理してよいです。

- API / contract
- domain
- repository
- usecase
- handler
- frontend
- unit test
- integration test
- e2e test
- 軽微なリファクタリング

ただし、これらは phase 分割の軸ではなく、phase 内部の実装順序や確認観点として扱ってください。

# 実行後の確認

最後に必ず以下を示してください。

- 参照した requirements.md と technical-design.md の要約
- 関連して確認した補助設計文書や既存実装のサマリー
- 洗い出したユースケース数
- 作成したフェーズ数
- 高リスクまたは要確認のフェーズ数
- 作成したファイルのパス
- 要件数に対して対応付けたフェーズ数

未確定事項やブロッカーがある場合は、着手前の確認を促してください。

# 後続フェーズとの接続方針

後続の実装作業は、各 phase ファイルを単位に進めてください。

ただし、業務要件の正本は requirements.md、技術設計の正本は technical-design.md です。タスク計画がそれらと矛盾する場合は、計画より先に上位文書を見直してください。
