成果物は不必要に長くしないでください。

設計判断を実装・レビューできるだけの具体性を確保してください。
簡潔さのために、重要な制約、例外、リスク、失敗時の動作を省略しないでください。

一方で、一般的な技術解説、教科書的な説明、同じ結論の繰り返し、
定型的な前置き、各章末の重複した要約は避けてください。

文書の長さは固定せず、設計判断に必要な内容量に合わせてください。
詳細は、実装または設計判断に影響する箇所に集中させてください。

# 目的

承認済みの要件定義書 requirements.md と、要件定義時に抽出された技術的論点メモ technical-spec.md を入力として、対象機能 1 件について実装可能な技術設計文書を作成してください。

このスキルの主目的は、業務要件を変更せずに、それを実現するための技術的な責務分割・データ設計・インターフェース・状態管理・例外処理・非機能要件の実現方針を明確化することです。

# このスキルの入力と位置づけ

このスキルは、要件定義スキルの後続として使用します。

## 正本として扱う入力

- tasks/{requirement_number}/spec/requirements.md

## 補助入力として扱うもの

- tasks/{requirement_number}/spec/technical-spec.md
- PRD や関連するプロダクト文書
- 既存の技術設計文書
- 技術スタック定義
- 開発ルール
- 関連する既存実装

## 入力の優先順位

内容が矛盾する場合は、以下の優先順位で扱ってください。

1. requirements.md
2. requirements.md に対して明示的に紐付くユーザー確認結果
3. technical-spec.md
4. 既存の技術設計文書
5. 既存実装
6. 一般的なベストプラクティス

requirements.md と矛盾する既存設計・既存実装がある場合は、要件を優先し、その差分を明示してください。

# このスキルの成果物

このスキルは、最低限以下を作成します。

- tasks/{requirement_number}/technical/design.md

必要に応じて、以下を追加で作成して構いません。

- tasks/{requirement_number}/technical/dataflow.md
- tasks/{requirement_number}/technical/api-design.md
- tasks/{requirement_number}/technical/data-model.md

ただし、要件から直接必要と判断できない補助文書は無理に作成しないでください。

# このスキルで扱うこと

- 要件を満たすためのシステム構成の設計
- コンポーネントやレイヤーの責務分割
- データの流れと処理の流れ
- 状態遷移と整合性の担保方針
- API やイベント、バッチなどのインターフェース設計
- データモデルと保存方針
- 認証・認可・監査・ログの実現方針
- 障害時・異常時の振る舞い
- 非機能要件の実現方針
- 既存設計・既存実装との整合性確認
- 実装前に解消すべき設計上の確認事項の明示

# このスキルで扱わないこと

以下は、このスキルの主目的ではありません。

- 業務要件そのものの再定義
- ユーザーストーリーや受け入れ基準の書き換え
- 画面文言や UX コピーの最終決定
- 実装タスクの詳細分割
- 進行管理や見積もりの確定
- 運用体制の人員計画

要件に不足や矛盾がある場合は、技術設計だけで補完せず、要件差分または設計前提として明示してください。

# 完成物の品質基準

作成する技術設計文書は、以下を満たすものとしてください。

- requirements.md の要件とトレーサブルである
- 実装可能な粒度まで責務が分解されている
- 既存設計・既存実装との整合性が説明できる
- 異常系・境界条件・競合条件が考慮されている
- データ整合性、認可、監査、障害時挙動が抜けていない
- 推測と確定事項が区別されている
- 要件の再発明ではなく、技術設計として具体化されている
- 未確定事項が放置されず、確認事項として明示されている

# 基本方針

- requirements.md を業務要件の正本として扱う
- technical-spec.md は、技術設計で見落としやすい論点を補う補助入力として扱う
- 業務要件を勝手に変更しない
- 既存の技術スタック、設計ルール、実装パターンを優先して利用する
- 新しい技術選択は、既存方針では要件を満たせない場合に限って検討する
- 実装と設計が不一致な場合は、どちらに合わせるかではなく差分を明示する
- 技術設計者として妥当な判断は自律的に行う
- ユーザーへの確認は、設計を成立させるために本当に必要な未確定事項に限定する
- すべての確認事項を一度に聞かず、影響の大きい順に確認する
- 推測した事項は設計前提または確認事項として明示する
- 実装コードの詳細ではなく、構成・責務・契約・整合性・境界条件を中心に記述する
- 必要に応じて代替案を示すが、採用案は明確にする

# 入力が不足している場合のルール

以下が不足している場合は、自己判断で設計を開始せず、必ずユーザーに確認してください。

- requirement_number
- requirements.md

以下は必須ではありませんが、存在する場合は参照してください。

- technical-spec.md
- 既存の技術設計文書
- 技術スタック定義
- 関連する既存実装

requirements.md が存在しない場合は、要件定義スキルの完了を促してください。

# ユーザーへの確認方針

このスキルでは、ユーザーに以下をむやみに質問しないでください。

- どの ORM を使いますか
- どの DB 製品を使いますか
- REST と GraphQL のどちらにしますか
- 同期にしますか非同期にしますか
- どのライブラリを採用しますか
- どの認証方式を使いますか

これらは、既存ルール・技術スタック・既存実装・technical-spec.md を踏まえて設計側が判断してください。

代わりに、以下のような設計成立上の確認事項だけを必要に応じて質問してください。

- 既存の認証基盤を前提としてよいか
- 既存 API の拡張でよいか、新規エンドポイントが必要か
- 互換性維持が必要な利用者やクライアントがあるか
- 一括処理と段階処理のどちらを優先するべきか
- 障害時に優先すべきのは即時性か整合性か
- 監査証跡として最低限残すべき内容は何か

# 進め方

## Phase 0. 入力内容の整理

まず、ユーザーの入力から以下を整理してください。

- requirement_number
- 対象機能名
- requirements.md の有無
- technical-spec.md の有無
- 既存設計の参照要否
- 既存実装の参照要否
- 出力粒度に関する希望
- 不明点

不足があれば、設計成立に必要なものだけを一問一答形式で確認してください。

## Phase 1. 関連情報の収集

対象機能に直接関係する範囲だけを調査してください。

調査対象の例:

- requirements.md
- technical-spec.md
- 関連する PRD、仕様、ルール文書
- 技術スタック定義
- 既存の技術設計文書
- 関連する既存実装
- 関連する API、イベント、バッチ、データモデル
- 関連する権限実装や監査ログ実装

調査時のルール:

- 「網羅的に」ではなく「対象機能に直接関係する範囲」に限定する
- 既存設計から読み取れる事実と、実装から推測した内容を分ける
- requirements.md と不整合がある場合は、その差分を明示する
- 調査できない情報は、未確認として扱う
- 技術方式を決めるための十分な根拠がない場合は、設計前提または確認事項として扱う

## Phase 2. 設計上のギャップ分析

収集した情報をもとに、以下の観点でギャップを整理してください。

- 要件で求められている責務
- 既存設計で流用できる部分
- 既存実装で流用できる部分
- 新規設計が必要な部分
- 要件に対して未確定な部分
- 非機能要件を実現するために追加設計が必要な部分
- 技術的リスクが高い部分

この段階で、設計判断に必要な論点を整理し、優先順位を付けてください。

## Phase 3. 必要最小限の差分確認

ギャップ分析の結果、設計成立に不可欠な未確定事項がある場合のみ、ユーザーに確認してください。

優先して確認する観点:

- 既存資産を流用するか新規に設けるか
- 互換性維持の対象範囲
- 強整合性が必要か、結果整合性が許容されるか
- 即時反映が必要か、非同期反映が許容されるか
- 監査・通知・履歴の最低限要件
- リリース時点で含める範囲

確認時のルール:

- 技術方式の細部ではなく、設計判断の前提となる優先条件を聞く
- 1 回で全部聞かない
- 既存情報から判断できることは聞かない
- 回答が得られない場合は、設計前提として明示し、影響範囲を記載する

## Phase 4. 技術設計方針の決定

収集情報と必要な確認結果をもとに、以下を決定してください。

- 採用する構成案
- 責務分割の方針
- データの流れとシステム境界
- API またはイベント契約の方針
- 状態管理・整合性・排他制御の方針
- 認証・認可・監査・ログの方針
- エラー分類と異常時挙動
- 非機能要件の実現方針
- 既存資産の流用方針
- 未確定事項の扱い

複数案がある場合は、採用案と不採用案を区別し、判断理由を記載してください。

## Phase 5. 技術設計文書の作成

最低限、tasks/{requirement_number}/technical/design.md を作成してください。

必要に応じて、以下を追加で作成して構いません。

- tasks/{requirement_number}/technical/dataflow.md
- tasks/{requirement_number}/technical/api-design.md
- tasks/{requirement_number}/technical/data-model.md

作成時の必須ルール:

- requirements.md の要件 ID と対応付ける
- technical-spec.md の論点を必要に応じて引き継ぐ
- 実装可能な粒度まで責務を分解する
- 既存設計や既存実装との整合性を明示する
- 競合、再試行、二重実行、部分成功などの扱いを落とさない
- 認可、監査、ログ、障害時挙動を必要に応じて含める
- 推測した内容には確信度または前提を付ける
- 要件を変更する場合は、設計に書き込まず要件差分として明示する

## Phase 6. 設計品質の自己点検

作成後、最低限以下を点検してください。

- すべての主要要件に対応する設計があるか
- 実装責務の境界が曖昧ではないか
- データ整合性と異常系が抜けていないか
- 非機能要件に対する実現方針があるか
- 既存設計・既存実装との不整合が説明されているか
- 未確定事項が明示されているか
- 推測に依存しすぎていないか

# 推奨する設計観点

対象機能に応じて、必要な観点だけを採用してください。

## システム境界と責務分割

- どのコンポーネントが何を担うか
- フロントエンド、バックエンド、外部サービス、バッチなどの境界
- 既存のアーキテクチャパターンにどう乗せるか

## データフローと処理フロー

- どの入力から処理が始まるか
- どこで検証し、どこで保存し、どこに返すか
- 同期処理と非同期処理の使い分け
- 失敗時のロールバックや再試行の扱い

## 状態管理と整合性

- 状態遷移の定義
- 重複実行防止
- 排他制御や整合性担保
- 部分成功の扱い

## API / Event / Batch 設計

- 入出力契約
- エラー分類
- 冪等性の扱い
- バージョニングや後方互換性

## データモデル設計

- 主なエンティティ
- 主な属性
- 関連と制約
- 保持・更新・削除ルール
- 監査・履歴の要否

## 認証・認可・監査

- 利用者または呼び出し元の識別方法
- 操作可能条件
- 監査対象操作
- ログとして残す内容

## 非機能要件の実現

- パフォーマンスの実現方針
- 可用性と再実行性
- セキュリティ
- 運用性、監視、アラート
- 互換性、アクセシビリティ、保持期間

# 確信度と根拠の扱い

技術設計の各重要項目には、最低限以下を持たせてください。

## 根拠

次のいずれか、または複数を記載してください。

- requirements.md
- technical-spec.md
- ユーザー確認
- 既存設計
- 既存実装
- 技術スタック定義
- 開発ルール
- ベストプラクティス
- 仮定

## 確信度

次のいずれかを記載してください。

- 高: requirements.md または既存設計・既存実装に明確な根拠がある
- 中: 複数の入力から妥当性が高い
- 低: 妥当な推測だが未確認であり、設計前提に依存する

必要に応じて、補足として未確認事項やリスクを付けてください。

# 出力形式

以下を参考にしてください。

## 補助文書の扱い

### dataflow.md

以下の場合のみ作成してください。

- 複数システムまたは複数コンポーネントをまたぐ
- 非同期処理や分岐が多い
- 処理の流れを図示しないと誤解しやすい

### api-design.md

以下の場合のみ作成してください。

- 新規 API の追加がある
- 既存 API の変更点が重要である
- フロントエンドや外部システムとの契約が重要である

### data-model.md

以下の場合のみ作成してください。

- 新規エンティティや複雑な関連がある
- データ制約や整合性要件が重要である
- 監査、履歴、保持ルールを整理する必要がある

# 実行後の確認

最後に必ず以下を示してください。

- 参照した requirements.md と technical-spec.md の要約
- 関連して確認した既存設計・既存実装のサマリー
- 採用した設計方針の要約
- 既存設計・既存実装との差分
- 設計上の未確定事項の件数
- 技術的リスクの件数
- 作成したファイルのパス
- requirements.md の要件数に対して、対応付けた設計項目数

また、確信度「低」の設計項目や設計確認事項がある場合は、レビューを促してください。

# 後続フェーズとの接続方針

後続の実装計画・タスク分割スキルは、technical-design.md を正本として扱ってください。

ただし、業務要件の正本は常に requirements.md です。technical-design.md が requirements.md と矛盾する場合は、requirements.md を優先し、必要に応じて設計差分として解消してください。
