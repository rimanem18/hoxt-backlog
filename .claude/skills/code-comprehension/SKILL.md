# Code Comprehension

## 目的

AI が生成・変更したコードを、開発者が十分に理解しないままコミットすることを防ぐ。

コードが動作するかをレビューするだけではなく、開発者自身がその変更について以下を説明・判断できる状態か確認する。

- 何を変更したのか
- コードがどのような流れで動くのか
- なぜこの実装・設計になっているのか
- 他の設計と比較して妥当か
- どこにバグや保守上のリスクがあるか
- テストが何を保証し、何を保証していないか
- 問題が発生した場合に自分で調査・修正できそうか

このスキルはコードレビューそのものではなく、**開発者のコード理解度を検証するための短時間の口頭試問**として扱う。

目安として 5〜10 分程度で終了させる。

# Scope

まず現在の変更内容を確認する。

可能であれば以下を対象とする。

1. 変更されたファイル全体
2. 新規追加されたファイル
3. 変更に関連するテストコード
4. 変更されたコードから直接呼び出される重要な処理
5. 変更されたコードを直接呼び出している重要な処理

基本的には diff だけを見るのではなく、**変更されたコードがファイル全体の中でどのような役割を持っているか**を把握してから出題する。

ただし、短時間の確認という目的を維持するため、関連コードを無制限に探索しない。

# Workflow

## Step 1: Inspect the Changes

変更されたファイルと関連テストを確認する。

以下を内部的に整理する。

- 今回の変更目的
- 主な処理フロー
- 重要な関数・クラス・モジュール
- データの流れ
- 外部への副作用
- 設計上の重要な判断
- エッジケース
- テスト対象
- テストされていない可能性のある挙動

この時点では、理解内容をすべて開発者に説明しない。

先に説明すると試験の答えを与えてしまうためである。

## Step 2: Select Five Questions

変更内容に合わせて 5 問を選ぶ。

固定された質問を機械的に出すのではなく、その変更で理解しておく価値が最も高い箇所を選ぶ。

原則として以下のカテゴリを含める。

1. 全体理解
2. コード・データフロー理解
3. 設計判断
4. リスク・エッジケース
5. テスト理解

必要であればカテゴリを入れ替えてよい。

たとえば設計変更が大きい場合は、設計問題を2問出してもよい。

## Step 3: Ask One Question at a Time

質問は必ず **1 問ずつ** 出す。

5 問すべてを最初に表示してはいけない。

開発者の回答を見る前に、以下を出してはいけない。

- 正解
- 詳細なヒント
- 模範回答
- 答えを強く誘導する説明

質問は「コードを見れば文字列として答えられる問題」ではなく、理解が必要な問題を優先する。

# Question Design

## 1. 全体理解

開発者が変更を高いレベルで説明できるか確認する。

例:

- 今回の変更によって、システムの挙動は変更前からどう変わりましたか？
- この変更について、入力から出力までの処理フローを説明してください。
- このコミットの目的を、コードを見ていない別のエンジニアに説明するとしたらどう説明しますか？

単なるファイル一覧の説明ではなく、**挙動の変化**を説明できるかを見る。

## 2. コード・データフロー理解

重要な関数、条件分岐、状態変化について確認する。

例:

- この値はどこで生成され、どの処理を通って最終的にどこで利用されますか？
- この関数がこのタイミングで呼ばれる理由を説明してください。
- この条件分岐を削除すると、どのような挙動になりますか？
- この関数が返す値は、その後どのコードでどのように利用されますか？

関数名やコードを暗記しているかではなく、**処理の因果関係を理解しているか**を見る。

## 3. 設計判断

AI が選択した設計を開発者自身が評価できるか確認する。

例:

- なぜこの責務をこのクラス／関数に持たせていると考えられますか？
- この実装以外にどのような設計が考えられますか？
- 現在の実装を別案と比較した場合のメリット・デメリットは何ですか？
- この処理を呼び出し側に置く設計と、現在の設計では何が違いますか？

唯一の正解を要求しない。

重要なのは、現在の設計を無条件に受け入れるのではなく、**トレードオフを考えられること**である。

## 4. リスク・エッジケース

正常系以外を考えられるか確認する。

例:

- この変更でバグが発生するとしたら、どこが最も怪しいですか？
- この処理に想定外の値が入った場合どうなりますか？
- この条件の境界値ではどのような挙動になりますか？
- 外部 API や DB が失敗した場合、このコードはどの状態になりますか？
- 将来この仕様を拡張するとき、変更しづらそうな箇所はありますか？

コード中に実際に存在するリスクを優先する。

存在しない問題を無理に作らない。

## 5. テスト理解

テストコードを読めるだけでなく、テストの保証範囲を理解しているか確認する。

例:

- このテストは具体的にどの挙動を保証していますか？
- このテストが失敗した場合、どの部分に問題がある可能性がありますか？
- なぜこのケースをテストしているのでしょうか？
- 現在のテストでは保証されていないケースはありますか？
- 実装のこの条件分岐は、どのテストによってカバーされていますか？

「テストが通るから安全」という回答を十分な理解とはみなさない。

# Reverse Reasoning Question

可能であれば5問のうち1問は、通常の説明問題ではなく**逆方向から考える問題**にする。

例:

- この関数を削除した場合、最初にどこが壊れると思いますか？
- この条件を反転したら、どのテストが失敗すると思いますか？
- この値が常に `null` になったら、ユーザーから見える挙動はどう変わりますか？
- この処理の順序を入れ替えると何が起きますか？

逆方向の質問は、コードを表面的に読んでいるだけなのか、因果関係まで理解しているのかを判断するために使う。

# Evaluation

各回答を以下の3段階で評価する。

## A — 理解できている

以下を満たす。

- 重要なポイントを自分の言葉で説明できている
- コードの実際の挙動と矛盾していない
- 処理の理由や因果関係を説明できている

簡潔に評価し、次の質問へ進む。

## B — 概ね理解している

大筋は正しいが、重要なポイントが不足または曖昧。

以下の順で返す。

1. 正しく理解できている部分
2. 不足している部分
3. 必要最小限の補足

補足後、原則として次の質問へ進む。

## C — 理解不足

以下のいずれかに該当する。

- 重要な処理を誤解している
- コードの実際の挙動と回答が異なる
- 設計意図について根本的な理解が不足している
- コードを自分で説明できていない

以下を簡潔に説明する。

1. どこが違うか
2. 実際のコードではどうなっているか
3. なぜその挙動になるか

その後、必要であれば理解確認の追加問題を1問出す。

追加問題は5問の本試験とは別として扱う。

# Adaptive Difficulty

質問の難易度は変更内容に応じて調整する。

## 軽微な変更

以下を中心にする。

- 処理フロー
- 条件分岐
- テスト

5問以内で速やかに終了する。

## 通常の機能変更

以下をバランスよく確認する。

- 全体理解
- 処理フロー
- 設計
- リスク
- テスト

## 高リスクな変更

以下を含む変更では、設計・障害時挙動・データ整合性を優先する。

- 認証・認可
- DB 更新
- トランザクション
- 並行処理
- 非同期処理
- キャッシュ
- 状態管理
- 課金
- セキュリティ
- 外部 API
- データ削除
- migration

ただし、5〜10分程度という目的を維持する。

問題数を大量に増やすのではなく、重要度の低い質問を高リスク領域の質問に置き換える。

# Design Sanity Check

5問の試験とは別に、変更された設計について一度だけ検討する。

次の観点で考える。

> このコードが現在正常に動くかではなく、この設計を今後半年保守するとしたら何が気になるか。

確認する候補:

- 責務が適切に分離されているか
- 不必要に抽象化されていないか
- 重複した状態を持っていないか
- 呼び出し関係が複雑になっていないか
- 隠れた副作用がないか
- テストしづらい構造になっていないか
- 将来の仕様変更に対して過度に硬直していないか
- AI が必要以上に複雑な実装を生成していないか

具体的な懸念がある場合のみ指摘する。

問題が見つからない場合は、無理に問題を作らず、

「大きな設計上の懸念は見当たらない」

と判断する。

# Final Assessment

5問終了後、まとめを出す。

以下の形式を使用する。

## 理解度

`A` / `B` / `C`

## コミット判定

### PASS

変更内容、処理フロー、設計、リスク、テストを十分理解している。

自分で他のエンジニアに説明し、問題発生時に調査・修正できると判断できる。

### CAUTION

大筋は理解しているが、重要な箇所の理解が曖昧。

コミット前に確認すべきポイントを具体的に示す。

### FAIL

重要な処理または設計を十分理解できていない。

理解すべきファイル、関数、処理を具体的に示す。

## 理解が弱かったポイント

最大3つ挙げる。

理解に問題がなければ「特になし」とする。

## 設計上の懸念

Design Sanity Check の結果を簡潔に示す。

## この変更を一言で説明すると

最後に、

「このコミットでは何を、なぜ、どのように変更したのか」

について、他のエンジニアに説明するときの模範的な説明を3〜5文で示す。

これは試験中には表示せず、すべての回答が終了した後にのみ表示する。

# Important Rules

- 最初からコードの解説をしない
- 問題は必ず1問ずつ出す
- 開発者が回答する前に正解を出さない
- 細かい構文知識より、処理・設計・因果関係を優先する
- AI が書いた設計を正しいものとして扱わない
- コードが動くことと、設計が妥当であることを区別する
- テストが通ることと、十分にテストされていることを区別する
- 開発者の回答が多少言葉足らずでも、本質を理解していれば過度に減点しない
- 存在しない問題や設計上の懸念を無理に作らない
- 試験そのものが目的にならないよう、5〜10分程度で終える

# Start

変更されたファイル全体と関連するテストコードを確認する。

変更内容を内部的に整理した後、解説を先に行わず、

**「第1問」**

から試験を開始する。
