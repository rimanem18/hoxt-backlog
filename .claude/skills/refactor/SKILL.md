## 概要

ボーイスカウトルールに基づいて、特定のタスクでさわったファイル、またはこのスキル使用時に示された条件に基づいてファイルをキレイにしてください。ただし、フォーマットしかされていないファイルは、分析対象にしないでください。

既存のコードにとらわれず、より良いコードにすることを目指してください。

リファクタリング対象が不明確な場合は、 ask_user ツールでユーザーに質問してください。質問をする際には事前に関連するコードを分析して、具体的な質問をするようにしてください。

以下の加点 / 減点基準に基づいて得点付けをして、費用対効果の見積もりをします。

### 加点 / 減点基準:

- 安全に小さく変更が可能(+4pt)
- デザインシステムに従っていない箇所を修正(+3pt)
- ガイドラインに反する箇所の修正(+3pt)
- テストコードの雑なキャスト（`as never` 等、型エラー回避目的の型アサーション）を、共通 factory / helper への集約、または型を狭めた構造（Pick / adapter / view model）に置き換える(+3pt)
- デッドコードの削除(+3pt)
- ドメインロジックが Domain 層以外に混入しており、それを Domain 層に移行する(+3pt)
- アプリケーションロジックが Application 層以外に混入しており、それを Application 層に移行する(+3pt)
- インフラロジックが Infrastructure 層以外に混入しており、それを Infrastructure 層に移行する(+3pt)
- Entity 化 / Value Object 化などにより、ドメインモデルが充実する(+3pt)
- Domain 層以外がビジネスルールを知ってしまっており、それを改善できる(+3pt)
- Repository の責務が単純化する(+3pt)
- 手動で作成したユーティリティ関数やヘルパー関数が、ライブラリの機能やフレームワークの機能で置き換えられる(+3pt)
- React の入力フォームのバリデーションロジックが Zod を使用した形に変更できる(+3pt)
- 重複ロジックを共通化して、hooks などの別のファイルに切り出せる(+3pt)
- 工数が短く済む(+2pt)
- パフォーマンスが向上する(+2pt)
- 可読性が向上する(+2pt)
- メンテナンス性が向上する(+2pt)
- テスタビリティが向上する(+2pt)
- 再利用性が向上する(+2pt)
- 後方互換性を保つ必要がない(+2pt)
  - ユーティリティやヘルパー関数が参照が減る / 削除できる
- 価値の低いテストが削除できる(+2pt)
- YAGNI原則に反する可能性あり(-2pt)

## 手順

1. 関連するコミットのファイルのうち、 変更されたファイルをリストアップしてください。（コミットメッセージには {issue_number} が含まれているため、検索することも可能）
2. 加点基準に基づいた評価ができるように Explore サブエージェントを起動して関連ファイルのコードベースの分析をしてください。
3. 分析結果に基づいて、2～5個のリファクタリング提案をしてください。リファクタリングは変更範囲に限らず、関連するコード全体に対して行うことができます。
4. それらのアプローチのうち、加点基準に基づいて評価してください。
5. テストケースを洗い出します。テストの作成や削除も必要になると判断した場合、Red - Green - Refactor の TDD に従った変更を検討してください。
6. ユーザーに指示を仰ぎます。
