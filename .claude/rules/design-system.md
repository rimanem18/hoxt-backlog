# UI / UX

## 重要視すべき判断基準

このアプリケーションは、PC での使用も想定される必要がある。ただし、モバイルファーストのレイアウトにする。

- マウス・キーボードなど Web アプリケーションとしてのアクセシビリティ要件も満たす必要もあるが、あくまでスマートフォンでの使いやすさを最優先する。
- PC 向けレイアウトを縮小して流用するのではなく、スマートフォンの画面サイズ・操作性・通信環境を前提に設計する。
- 各画面では、ユーザーが達成すべき最重要タスクを明確にし、主要な操作を優先して配置する。
- 初期表示には本当に必要な情報のみを表示し、補足情報や詳細情報は折りたたみ・詳細画面・段階表示で扱う。
- レイアウトは縦スクロールを基本とし、不要な横スクロールを発生させてはならない。
- 表形式の情報は、そのまま横に詰め込まず、必要に応じてカード化・項目の絞り込み・詳細画面への分離を行う。
- 主要な操作ボタンは、スマートフォンで押しやすい位置と十分なタップ領域を確保する。
- アイコンのみで意味を伝える設計は避け、必要に応じてラベルや補助テキストを併記する。
- フォームはスマートフォンでの入力負荷を最小化する。入力項目は必要最小限とし、適切な入力方式・キーボード種別・選択 UI を使い分ける。入力負荷の最小化は、説明の削減ではなく、項目数・操作数・判断回数の削減によって行う。
- 保存・送信・次へ などの主要アクションは、ユーザーが見失わないように明確に配置する。必要に応じて固定フッター等を用いる。固定フッターを用いる場合は、ソフトウェアキーボード表示時・セーフエリア・小画面端末で主要入力や操作を妨げないことを確認する。
- 文字サイズ、余白、行間、情報の強弱を適切に設計し、狭い画面でも読みやすさと視認性を確保する。
- UI は片手操作を意識し、無理な持ち替えや過度な精密操作を要求してはならない。
- スマートフォン特有の挙動を考慮する。ソフトウェアキーボード表示時、セーフエリア、画面サイズ差異、縦横比の違いで破綻しないように実装する。
- 低速回線や性能の低い端末でも過度な負荷を与えないよう、初期表示速度・画像サイズ・描画量に配慮する。
- PC 版との完全一致を目的にしない。スマートフォンでの使いやすさを優先し、必要であれば情報量・導線・操作フローを変えてよい。

## HIG（Apple の Human Interface Guidelines）に基づく設計判断基準

Apple の Human Interface Guidelines（HIG）に見られる考え方を、Web フロントエンド実装の判断基準に基づいてください。

ただし目的は、Apple 風の見た目を表面的に模倣することではありません。  
重要なのは、**明瞭で、控えめで、理解しやすく、操作しやすい UI** を一貫して作ることです。

Tailwind CSS や shadcn/ui などの具体的な実装手段には依存せず、それらの上位にある判断基準として使ってください。

- この UI は理解しやすいか
- 情報の優先順位が明確か
- 装飾が主役を邪魔していないか
- 状態変化や操作結果が十分に伝わるか
- 誤操作しにくいか、または取り戻せるか
- 動きやレイヤー表現に意味があるか
- 一貫性があり、学習コストが低いか

デザインレビュー、コンポーネント設計、UI 実装レビューの基準として使うことを想定しています。

## 基本思想

Apple の UI / UX は、主に次の 3 つのテーマで語られることが多いです。

### Clarity（明瞭さ）

情報が読みやすく、構造が理解しやすく、操作対象が明確であること。  
ユーザーが迷わず認識できることを優先します。

### Deference（控えめ・コンテンツ優先）

UI は主役ではなく、コンテンツやタスクの理解と操作を助ける存在であること。  
装飾や演出は必要最小限にとどめます。

### Depth（奥行き）

レイヤー構造、状態変化、遷移の意味が伝わること。  
視覚的な前後関係やモーションによって、今どこにいて何が起きたかを理解しやすくします。

## 設計原則

実装やレビューでは、次の原則を判断軸にしてください。

### Aesthetic Integrity（美的整合性）

見た目の美しさそのものではなく、  
**機能・文脈・見た目が一致しているか** を重視します。

- 業務画面なのに過度に装飾的ではないか
- 危険操作なのに軽い見た目になっていないか
- 情報密度と余白設計が文脈に合っているか

### Consistency（一貫性）

同じ意味・同じ状態・同じ操作には、同じ表現を使います。一貫性とは、全デバイスで完全に同一レイアウトにすることではなく、同じ意味・同じ状態・同じ操作に対して、文脈に応じた一貫した表現を保つことを指します。

- 同じ種類のボタンが画面ごとに見た目や文言を変えていないか
- エラー表示、ローディング、無効状態の扱いが統一されているか
- 余白、角丸、境界線、タイポグラフィのルールが一貫しているか

### Direct Manipulation（直接操作）

対象を間接的に説明するより、  
**対象そのものを自然に扱える** ほうが理解しやすいです。

- 対象物がどれか分かりやすいか
- どこを触れば何が起きるかが直感的か
- 操作対象と結果の対応が近いか

### Feedback（フィードバック）

入力や処理に対して、結果や状態を即時に返します。

- 押せたのかどうか分からない UI になっていないか
- 保存中・送信中・完了・失敗が明確か
- フォーカス、ホバー、押下、選択、無効、エラーが見分けられるか

### Metaphors（メタファ）

必要な範囲で、直感的に理解できる比喩や慣習を使います。  
ただし、見た目の演出を優先して複雑にしないこと。

### User Control（ユーザーの制御）

システムが勝手に決めすぎず、ユーザーが意図を維持できるようにします。

- 取り消しややり直しの余地があるか
- 破壊的操作に確認や回復手段があるか
- 自動遷移や自動確定が過剰ではないか

## 実装判断の指針

### 情報設計

情報は、色や装飾よりも **順序・余白・見出し・グルーピング** で理解させます。

- 見出し、本文、補足、注記、エラーの階層を明確にする
- 近いものは近く、異なるものは離して配置する
- 線や影を増やす前に、余白と整列で解決できないか考える
- 1 画面に複数の主目的を置きすぎない

### タイポグラフィ

可読性を優先します。

- 小さすぎる文字を使わない
- 本文と補助情報の差を適切につける
- コントラスト不足を避ける
- 長文では行間を十分に確保する
- 強調は太字・サイズ・位置で行い、色だけに依存しない

### 色と装飾

色は意味を伝えるために使い、飾るためだけには使いません。

- プライマリアクション、注意、破壊的操作の意味を明確に分ける
- 装飾的なグラデーションや過度なシャドウを常用しない
- 境界線、背景差、影の役割を重複させない
- ライト / ダークモードで意味が崩れないようにする

### レイヤーとモーション

動きには必ず意味を持たせます。

- モーダル、ドロワー、ポップオーバーなどの前後関係を明確にする
- アニメーションは注意誘導や状態変化の理解に寄与する場合だけ使う
- 常時動く UI や過度なエフェクトは避ける
- motion reduction への配慮を前提にする
- 奥行きやモーションは、明瞭さや操作理解を高める場合に限って用いる。迷った場合は、演出よりも明瞭さと控えめさを優先する。

### 操作性

操作しやすさを見た目より優先します。

- クリック / タップ領域は十分に確保する
- フォーカス可能要素はキーボード操作で辿れるようにする
- アイコンだけの操作には必要に応じてラベルや説明を補う
- 危険操作は通常操作と距離や見た目を分ける
- 読み込み中に押せるのか押せないのかを曖昧にしない

### フォーム

フォームはとくに明瞭さと制御性が重要です。

- ラベルを省略しすぎない
- プレースホルダーをラベル代わりにしない
- ヒント、制約、エラーを混同しない
- エラーは原因と修正方法が分かるようにする
- 必須 / 任意 / 入力形式 / バリデーションタイミングを明確にする

## 具体的なレビュー観点

UI をレビューするときは、次の観点を優先してください。

### 明瞭さ

- 何の画面か一目で分かるか
- どこが主要アクションか分かるか
- 読み順が自然か
- 重要情報が埋もれていないか

### 控えめさ

- 装飾がコンテンツより目立っていないか
- 境界線、背景差、影、色の使いすぎがないか
- 強調箇所が多すぎて、逆に強調が成立しなくなっていないか

### 奥行きと状態変化

- 今の状態が分かるか
- 遷移や開閉に意味があるか
- モーダルやオーバーレイの階層が自然か

### フィードバック

- 押下、選択、フォーカス、エラー、成功、処理中が識別できるか
- 長い処理に待機状態や進捗があるか
- 保存や送信の結果が曖昧ではないか

### ユーザー制御

- 誤操作しにくいか
- 破壊的操作に適切な確認があるか
- 戻れるか、やり直せるか、キャンセルできるか
- 自動処理がユーザーの意図を奪っていないか

### 一貫性

- 同じ意味の UI が別の見た目や別の文言になっていないか
- コンポーネントごとに余白やタイポがばらついていないか
- 画面単位ではなく、プロダクト全体で揃っているか

## 禁止寄りの指針

次のような実装は避けてください。

- 目立たせるためだけの過剰な色や影
- 意味のないアニメーション
- 小さすぎて押しにくい操作要素
- プレースホルダー依存のフォーム設計
- フィードバックのない非同期処理
- 危険操作と通常操作が見分けにくい配置
- 同じ意味なのに画面ごとに違う見た目・違う文言
- 情報整理を装飾でごまかすこと
- Apple 風の見た目だけを模倣して、操作性や可読性を軽視すること
