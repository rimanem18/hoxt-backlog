# 進捗共有機能（上長向け）

タスクCRUD機能の次の展開として、上長（プロジェクトを横断して見ている人）が能動的な報告を受けなくても進捗・優先度を認知できる状態を作る。

以下の4つの要件に分解し、段階的に実現する。①は②③④すべての前提となるため最初に着手する。②は③④の前提となる。③と④は互いに独立して着手可能。

1. project基盤（project作成・taskとの紐付け）
2. viewer招待・閲覧
3. 通知
4. リアクション

---

# ① project基盤

## 要件定義

- `project` エンティティを新設し、`task` は `project` に属する
- 既存 `task` への `project_id` 外部キー追加（既存タスクの移行方針は要検討）

## 技術補足と制約

- **DBスキーマ変更**: `project` の追加、既存 `task` への `project_id` 外部キー追加
- スキーマ駆動フロー（generate:schemas → generate:openapi → generate:types）に従う

## スコープ外（今回は含めない）

- organization / backlog / backlogItem階層
  - 検討経緯: 当初 `organization ← project ← backlog ← backlogItem ← task` の階層を想定していたが、スプリント管理などの予定がなく、上長への共有は `project` 単位のviewer招待で十分なため、`project ← task` に簡素化した

# ② viewer招待・閲覧

## ユーザーストーリー

1. 上長として、複数プロジェクトのタスク進捗・優先度を、報告を受けなくても横断的に確認したい。
2. 上長として、アプリにアカウント登録せず（メールアドレス登録程度で）進捗を閲覧したい。

## 要件定義

### 招待・共有範囲

- `project` に対してviewerをメールアドレスベースで招待できる（アカウント登録不要）
- viewerは複数 `project` に横断して招待されうる。閲覧画面はviewerが招待されている全projectを横断集約表示する

### 閲覧

- viewerはトークン付きリンクからログインなしで、自分がviewer登録されている全projectのtask一覧を読み取り専用で閲覧できる

### 権限モデル

- viewerは閲覧のみ。ステータス変更・担当者変更などの編集権限は持たない

## 技術補足と制約

- **認証方式**: viewerはSupabase Authの正規アカウントを持たない想定。推測不能なランダムトークンによるマジックリンク方式で本人特定とアクセス制御を行う。トークンの失効・再発行の仕組みが必須（認証系はfail-closed。トークン検証失敗時は即時拒否）
- **RLSの限界**: viewerはSupabase Authユーザーではないため、既存のuser単位RLSだけでは完結せず、API層（Hono）でトークンベースのアクセス制御を別途実装する必要がある
- **DBスキーマ変更**: `project_viewers` の追加

## スコープ外（今回は含めない）

- viewerへの編集権限付与

# ③ 通知

## ユーザーストーリー

1. 上長として、タスクの優先度が変わったときに、自分から見に行かなくても気づきたい。
2. 上長として、通知を受け取るプロジェクトを自分で選びたい（全部だとノイズになるため）。

## 要件定義

- 以下のイベント発生時、対象projectの通知ON状態のviewerに通知する
  - タスクが追加された
  - ステータスが変わった
  - 優先度が変わった
- 通知手段はWeb Push（デスクトップ想定、第一候補）とメール（併用/フォールバック）
- **優先はリアルタイム都度通知**。ダイジェスト（まとめ配信）は現時点では不要と判断するが、潜在需要はあるため将来の拡張点として設計上考慮しておく
  - ダイジェストを実装する場合、配信時刻（時・分）は viewer 本人が指定できる方式を優先する。難しければ project 作成者（部下）が project 単位で代表指定する方式でも可
  - 補足: viewer個別指定はトークン付き設定ページに時刻フィールドを追加するだけで済むが、スケジューリング側はviewerごとの時刻に合わせて短間隔（毎分〜5分おき等）でバッチを回す必要がある。部下による代表指定ならproject単位の1時刻でよく、スケジューリングは単純な日次cronのままで済む
- viewerはproject単位で通知ON/OFFを設定できる
- （検討中）部下（タスク作成者/変更者）への通知。viewerのリアクション発生時などを想定。部下は既存のSupabase Authアカウントを持つため、viewer向けのマジックリンク基盤は不要で、アプリ内通知一覧（＋任意でWeb Push基盤の流用）で実現できる見込み

## 技術補足と制約

- **Web Push**: Service Worker + Push API、VAPID鍵管理が新規インフラ要素として必要。iOS Safariは対象外（PWA化必須のため今回は考慮しない）
- **メール送信**: Amazon SESを想定
- **通知配信方式**: タスク変更（追加/ステータス変更/優先度変更）はDB更新と同一トランザクションで通知イベントテーブル（例: `task_notification_events`、Outboxパターン）にINSERTし、非同期ワーカーがpendingイベントを拾ってWeb Push/メール送信を行う
  - 理由: リクエストパス上でSES/Web Push送信の同期リトライを行うのはCLAUDE.mdの方針（リクエストパス上での無条件長時間リトライ禁止）に反するため、配信を別プロセスに分離する。ワーカー側のリトライは5xx/タイムアウトなど限定的なallowlistに基づく
  - 現時点ではこのイベントテーブルを使い「都度リアルタイム配信」のみ実装する。ダイジェスト配信は将来必要になった場合、イベントの書き込み側（use case実装）を変更せず、集計バッチ処理を追加するだけで対応できる見込み
- **DBスキーマ変更**: `task_notification_events` の追加

## スコープ外（今回は含めない）

- Slack連携（管理者承認が必要になるため保留）
- ダイジェスト配信（将来の拡張点として設計上のみ考慮）

# ④ リアクション

## ユーザーストーリー

1. 上長として、気になったタスクに軽くリアクションで反応を伝えたい。
2. 部下として、上長からの疑問に先回りして答えられるよう、優先度判断の根拠をタスクに残しておきたい。

## 要件定義

- viewerはタスクに絵文字リアクションを付けられる
- 優先度判断の根拠は新規フィールドとしては明示しない。既存のtask説明/メモ欄で代替可能

## 技術補足と制約

- **DBスキーマ変更**: `task_reactions` の追加

## スコープ外（今回は含めない）

- viewerのコメント機能（保留）
  - 判断材料: 現設計（`project_viewers` のトークンでviewerを識別）のまま `task_comments` テーブルを後付けするだけで済み、認証方式や識別の仕組み自体を作り直す必要はない
  - ただし後から追加する場合、以下は現設計に含まれていない新規要素になる
    - 自由記述の書き込みに対する乱用対策（レート制限・文字数制限など）。リアクションは選択式のため不要だったチェックが新たに要る
    - コメントが付いたことを部下側に知らせる通知経路（現設計の通知は「更新→viewer」の一方向のみで、「viewer→部下」の逆方向は未設計）
- スレッド型コメント、既読管理の詳細
